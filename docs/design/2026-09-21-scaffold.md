# 설계: 팀 스캐폴딩 하네스 (코어 + 프로젝트 두 계층)

| 항목 | 내용 |
|------|------|
| 최종 갱신 | 2026-09-21 |
| 상태 | 승인됨 (2026-09-21) — 1·2단계 구현 완료(4.1.0), 3단계 대기 |
| 참여 | Guksu · Claude(작성) |

## 1. 목표와 완료 기준

국수 하네스를 개발팀들의 "기초 뼈대"로 쓸 수 있게 한다. CRA(Create React App)처럼 기본 구조는 코어가 주고, 각 팀은 규칙·스킬·훅·템플릿을 자기 것으로 얹는다. 팀이 커스텀한 뒤에도 코어 업데이트를 계속 받을 수 있어야 한다.

완료 기준:

- `npx guksu-harness init`으로 빈 저장소에 하네스 뼈대가 생기고 `check`가 error 0으로 통과한다.
- 팀이 규칙·템플릿·스킬을 추가하거나 고친 프로젝트에서 `update`를 실행해도 팀 파일이 덮어써지지 않고, 코어 파일은 갱신된다.
- v3.0.0 설치본이 `update` 한 번으로 새 구조로 옮겨진다(미수정 파일은 자동, 수정 파일은 충돌 안내).
- 기존 테스트 전체와 새 명령의 회귀 테스트가 통과한다.

## 2. 범위

**포함:**

- npm 실행 명령 `guksu-harness` (init · update · status · check · eject). 기존 `harnessManager.mjs`의 plan/apply/rollback을 감싼다.
- 규칙 파일 분리: 코어 규칙 사본 `.agents/harness-core-rules.md`(관리 파일) + 팀 규칙 `docs/harness-rules.md`(프로젝트 파일).
- 문서 템플릿의 3-way 병합.
- v3 설치본 변환.
- `init --ci`로 CI 검사 워크플로 템플릿 생성.
- 팀 커스텀 가이드 문서.
- 버전 4.0.0.

**제외:**

- 팀 프리셋 계층(여러 저장소에 같은 팀 설정 배포). 나중에 "프로젝트 하네스 묶음 내보내기/가져오기" 명령으로 다룬다.
- 코어 훅 스크립트의 3-way 병합. 훅은 확장만 허용한다.
- npm 배포 자체. 배포는 소유자가 직접 한다. 이 작업은 `package.json`과 배포 전 검사까지 준비한다.
- 실제 Claude Code·Codex 앱 안에서의 훅 실행 검증(이 환경에서 불가).

## 3. 시스템 구조

용어:

- 코어: 국수 하네스가 소유하고 업데이트하는 파일. 훅 스크립트, 코어 규칙 사본, 관리 도구, 공통 스킬.
- 프로젝트 파일: 팀이 소유하는 파일. 관리 도구가 처음 한 번 만들고 이후 건드리지 않는다.
- 공동 파일: 팀이 고칠 수 있고 코어 업데이트도 받는 파일. 문서 템플릿과 앱 등록 파일.
- 3-way 병합: 이전 원본·팀 수정본·새 원본 셋을 비교해 팀 변경과 코어 변경을 합치는 방법. 같은 줄을 둘 다 고쳤으면 충돌.
- eject: 코어 파일 하나를 프로젝트 소유로 전환하는 명령. 이후 그 파일은 업데이트를 받지 않는다.

계층:

```
[코어] 플러그인 = npm 패키지 (같은 저장소)
guksu-harness/
├── skills/                          공통 스킬 9종 (앱이 직접 로드)
├── skills/harness/assets/           규칙 원본 · 훅 원본 · 템플릿 원본
├── bin/guksu-harness.mjs            신규. init · update · status · check · eject
└── package.json                     신규. npm 배포

[프로젝트] 팀 저장소
my-service/
├── .agents/
│   ├── harness-install.json         설치 기록 (버전·해시·소유 등록)
│   ├── harness-core-rules.md        코어 규칙 사본 — 항상 덮어씀
│   ├── harness-base/                3-way 병합용 원본 사본 (템플릿) — 관리 도구 전용
│   ├── hooks/                       코어 훅 + 설정값 + 팀 훅
│   └── skills/                      (Codex) 팀 스킬
├── .claude/skills/                  (Claude Code) 팀 스킬
├── .claude/settings.json            Claude Code 등록
├── .codex/hooks.json                Codex 등록
├── docs/harness-rules.md            팀 규칙 — 코어 포인터 한 줄 + 팀 규칙. 처음 한 번만 생성
├── docs/templates/                  문서 템플릿 — 팀이 고치면 3-way 병합
├── docs/history/                    작업 기록
├── .github/workflows/harness-check.yml   (--ci 선택) PR마다 check 실행
└── CLAUDE.md / AGENTS.md            포인터
```

소유권 규칙:

| 파일 | 소유 | 업데이트 때 |
|---|---|---|
| 훅 스크립트, 코어 규칙 사본 | 코어 | 덮어씀. 고쳐져 있으면 충돌로 멈춤. `eject`로 소유 전환 가능 |
| 훅 설정값, 팀 규칙, 팀 스킬, 팀 훅, CLAUDE.md·AGENTS.md, CI 워크플로 | 프로젝트 | 건드리지 않음 |
| 문서 템플릿 | 공동 | 팀이 고쳤으면 3-way 병합. 겹치면 충돌 |
| 앱 등록 파일 | 공동 | 관리 도구가 넣은 항목만 갱신 |

3-way 병합의 원본: 설치·업데이트 시점의 원본을 `.agents/harness-base/`에 사본으로 둔다. 네트워크 없이 동작하고 이전 버전 패키지를 받을 필요가 없다(문답 3라운드에서 말한 `npm pack` 방식 대신 채택 — 이유: 오프라인·결정적). 이 디렉터리는 커밋한다(팀원 모두가 같은 원본 기준을 가져야 한다). 병합은 `git merge-file`을 쓰고 git이 없으면 충돌로 표시한다.

업데이트 흐름:

```
npx guksu-harness update
  1. 설치 기록에서 이전 버전 확인
  2. 파일마다 판정
       코어 파일    미수정 → 교체 / 수정됨 → 충돌
       템플릿       미수정 → 교체 / 수정됨 → 3-way 병합 (harness-base · 현재 · 새 원본)
       프로젝트 파일 건너뜀
  3. 미리보기 출력 → 적용 (백업 생성) → harness-base 갱신
  4. check 실행 → 결과 보고
```

v3.0.0 설치본 변환(`update`에 포함):

| 대상 | 처리 |
|---|---|
| `docs/harness-rules.md` (v3 원본 그대로) | 팀 규칙 형식(포인터 + 빈 팀 규칙)으로 교체하고 코어 사본을 `.agents/`에 생성 |
| `docs/harness-rules.md` (팀이 수정) | 충돌. 코어 사본은 생성하고, 팀 규칙 파일은 손대지 않는다. 팀이 코어 규칙 7개를 지우고 포인터를 넣도록 안내 |
| `docs/templates/*.md` | 추적 해시가 일치하면 harness-base에 원본 등록. 수정본이면 현재 번들 원본을 base로 등록하고 다음 업데이트부터 병합 |

명령:

| 명령 | 하는 일 |
|---|---|
| `init [--app both] [--profile basic] [--verifier] [--ci]` | 뼈대 생성. plan + apply 한 번에. 이미 설치되어 있으면 update로 안내 |
| `update [--only ...]` | 위 흐름 |
| `status` | 현재 `status`와 같음 |
| `check` | 구조 검사 + 상태 진단. error가 있으면 종료 코드 1. CI용 |
| `eject <경로>` | 코어 파일의 추적을 해제하고 프로젝트 소유로 전환. 확인 문구 요구 |
| `plan` / `apply` / `rollback` | 기존 관리 도구 명령. 세밀한 제어용으로 유지 |

## 4. 실행 방식과 역할

직접 실행. 역할 분리나 에이전트 팀은 쓰지 않는다. 구현은 아래 3단계로 나누고 단계마다 PR 하나를 만든다.

| 단계 | 내용 | 산출 |
|---|---|---|
| 1 | npm 명령 `bin/guksu-harness.mjs` + `package.json`, 규칙 파일 분리와 v3 변환, `eject`, `check` | 4.0.0 |
| 2 | 템플릿 3-way 병합(`harness-base`), `init --ci` 워크플로 템플릿 | 4.1.0 |
| 3 | 팀 커스텀 가이드 문서, 프로젝트 하네스 묶음 내보내기/가져오기(프리셋 대체) | 4.2.0 |

## 5. 안전장치와 권한

- 관리 도구는 프로젝트 파일을 절대 덮어쓰지 않는다. 코어 파일은 미수정일 때만 교체한다.
- `eject`는 되돌릴 수 없는 소유 전환이므로 명령에 확인 문구를 요구하고 백업을 남긴다.
- 훅의 보안 범위는 그대로다. 훅은 도구 실행 시점의 실수를 줄이며 우회를 막는 경계가 아니다. 팀 강제는 `check`를 CI에 두어 보완한다.
- npm 배포 권한은 소유자에게만 있다. 관리 도구는 배포하지 않는다.
- `.agents/harness-base/`는 원본 사본만 담는다. 시크릿이나 설정값은 들어가지 않는다.

## 7. 미해결 질문

- npm에 `guksu-harness` 이름이 비어 있는지 확인하지 못했다(이 환경에서 레지스트리 접근 불가). 배포 전 소유자가 `npm view guksu-harness`로 확인한다. 이미 있으면 `@guksu/harness` 같은 범위 이름으로 바꾼다.
- Codex 플러그인의 스킬 이름이 Claude Code처럼 접두어(`guksu-harness:`)로 구분되는지 확인하지 못했다. 구분되지 않으면 팀이 같은 이름의 스킬을 프로젝트에 만들 때 충돌할 수 있다. 팀 커스텀 가이드에 "코어 스킬과 다른 이름을 쓴다"를 넣어 우회한다.
- 대상 팀의 규모·앱 구성·저장소 수는 아직 모른다. 가정: 팀은 저장소 1~3개, 앱은 섞여 있을 수 있다 — 2026-09-21 이 가정 위에 진행하기로 합의(문답 1라운드 미답, 2라운드에서 방향 승인).
- 팀 프리셋 계층은 3단계 이후 실제 팀 요구가 나오면 다시 문답한다.
