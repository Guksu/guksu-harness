## 2. grill-me / grilling 심층 비교 — 설계 문답 개선 후보

`grilling`(본체 28줄)의 핵심은 문답을 **설계 트리**(결정이 하위 결정으로 가지치는 트리)로 모델링하고, 라운드마다 **프런티어**(전제가 이미 확정되어 지금 물을 수 있는 질문 전부)를 계산해 묻는 것이다.

### 우리 설계 문답과의 비교

| 축 | grilling | 우리 설계 문답 | 판정 |
|----|----------|---------------|------|
| 라운드 반복 | 있음 (프런티어 소진까지) | 있음 (최소 3라운드, 종합→질문→반영) | 동등 |
| **질문 선정** | **프런티어 — 전제 확정된 질문 전부, 열린 질문에 의존하면 다음 라운드로 유예** | 주제 사다리 (목표→도메인→실행방식→종합, 고정 4주제) | **grilling 우세** — 사다리는 정적, 프런티어는 의존관계 기반 동적 |
| **사실 조사** | **"사실 찾기는 사용자가 아니라 에이전트의 일" — 라운드 중 필요한 사실은 서브에이전트로 조사, 조사 중에도 나머지 프런티어는 비차단 진행** | Phase 0 사전 조사 + "파악한 것은 묻지 않는다" — 라운드 **중** 새로 필요해진 사실의 처리 규칙 없음 | **grilling 우세** |
| **종료 기준** | 프런티어 소진 = "모든 가지 방문, **침묵된 가정 없음**" | 3조건 (새 미해결 0 + 모순 0 + 승인) | **상호 보완** — "침묵된 가정 0"이 더 강한 요구. 우리 "미해결 질문"은 *알려진* 미해결만 잡고, 몰래 깔린 가정은 못 잡는다 |
| 추천안 제시 | 질문마다 ➡️ 추천 답 | 추천안 첫 번째 + "(추천)" + 트레이드오프 양쪽 균형 서술 | 동등 (우리가 더 구체적) |
| 질문 품질 규칙 | 없음 | 쉬운 말 6규칙 (용어 풀이·선택지 결과 병기·유도 금지 등) | **우리 우세** |
| 기록·감사 추적 | 없음 (grill-with-docs가 domain-modeling과 조합해 보완) | 설계 문서 즉시 반영·라운드별 문답 기록·번복 보존 | **우리 우세** |
| 시간·수렴 안전장치 | 없음 | 30분~1시간 예산, 무한 문답 방지(변형 3라운드 반복 시 추천안으로 결정 요청) | **우리 우세** |

### 반영 제안 (design-dialogue.md 대상)

1. **프런티어 규칙 도입.** 주제 사다리는 "출발점"으로 유지하되(§3 첫 줄이 이미 그렇게 선언), 각 라운드의 질문 선정 기준을 명문화한다: *"한 라운드에는 전제가 이미 확정된 질문 전부를 묻는다. 이번 라운드의 다른 열린 질문의 답에 의존하는 질문은 다음 라운드로 미룬다."* 현재 §2의 "2~4개"는 개수 기준만 있고 선정 기준이 없다 — 의존 질문을 같은 라운드에 섞으면 사용자가 가정 위에 답하게 된다.
2. **사실/결정 분리 명문화.** *"결정은 사용자의 것, 사실은 에이전트의 것."* 라운드 중 질문의 전제가 되는 사실(파일 존재·스택 버전·기존 컨벤션 등)이 필요해지면 사용자에게 묻지 않고 직접/서브에이전트로 조사하고, 조사가 도는 동안 나머지 질문은 비차단으로 진행한다. 규칙 7(대량 읽기 서브에이전트 격리)과도 일관된다.
3. **종료 조건에 "침묵된 가정 0" 추가.** 설계 문서에 **가정 목록**을 두고, 문답 중 확인 없이 깔고 간 가정을 적출해 ①확인 질문으로 전환하거나 ②"이 가정 위에 진행" 합의를 받는다. 종료 조건 ①(새 미해결 질문 없음)을 "새 미해결 질문·미확인 가정 없음"으로 확장.
4. **(선택) 종합을 결정 트리 형태로.** 매 라운드 종합(§2-1)을 평문 요약 대신 "결정 → 그로 인해 열린/닫힌 하위 결정" 트리로 쓰면 모순 점검과 프런티어 계산이 같은 자료구조에서 나온다. 문서 부피가 늘어나므로 신규 구축 규모일 때만.

### C. 도입 불필요 (근거 포함)

- **git-guardrails-claude-code** — 우리 훅이 이미 상위 호환: `blockGitMutation.mjs`가 merge·rebase·reset·checkout·restore·clean·branch -D·stash까지 차단하고, 시크릿 훅·branchGuard·deny 2중 방어까지 있다. 저쪽은 push+파괴 명령 5종 차단이 전부.
- **wayfinder** — "안개 속 대형 계획을 결정 티켓 지도로" 발상은 흥미롭지만 이슈 트래커 인프라에 강결합. 다세션 설계는 우리 handoff+설계 문서 갱신으로 커버 중. 설계 문답이 한 세션을 넘는 사례가 실제로 반복되면 그때 재검토.
- **ask-matt**(스킬 라우터) — 우리는 harness 스킬 description과 README FAQ가 라우팅을 담당. 스킬 수가 더 늘면 재검토.
- **wait-what** — "그 설명 못 알아들었으니 다시 쉬운 말로" 1문장 스킬. 절대 규칙 8이 원인을 차단하는 접근이라 중복. 다만 "사용자용 재설명 트리거"라는 UX는 참고 가치.
- **research / to-spec / to-tickets / triage / implement** — GitHub 이슈 트래커 중심 개발 플로우로, 하네스 **가** 아니라 하네스가 만들어줄 **도메인 스킬**의 영역. harness가 개발 도메인 하네스를 구축할 때 참고 자료로는 유효.
- **setup-pre-commit / scaffold-exercises / migrate-to-shoehorn / teach / writing-beats·fragments·shape** — 도메인이 다르거나(강의 제작·글쓰기) JS 툴체인 특화.
