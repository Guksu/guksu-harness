# 5.0.0 릴리스 준비와 최소 구성 후속 문서 정리

| 항목 | 내용 |
|------|------|
| 날짜 | 2026-09-25 |
| 브랜치 | release/5.0.0 |
| PR | https://github.com/Guksu/guksu-harness/pull/26 |
| 관련 경로 | package.json, .claude-plugin/, .codex-plugin/, CHANGELOG.md, README.md, skills/, docs/templates/history.md |

## 1. 개요

버전을 5.0.0으로 올리고, 최소 구성 PR(#25) 뒤에 남은 낡은 문서와 `import` 결함 1건을 고쳤다. npm 배포는 하지 않았다(이 환경에 npm 로그인이 없다). 머지 후 `npm publish`로 배포한다.

배경: PR #25로 옵션 없는 `init`이 기록 양식 없는 minimal을 설치하게 됐다. 설치 결과가 달라지므로 주 버전을 올렸다. npm에는 4.2.0만 배포되어 있고, 4.2.0은 `npx guksu-harness …`가 아무것도 하지 않고 종료 코드 0으로 끝난다(4.2.1에서 고쳤지만 배포하지 않음). 5.0.0을 배포해야 npx로 쓸 수 있다.

## 2. 작업 내용

- 버전: `package.json`, `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `.codex-plugin/plugin.json`을 4.2.1 → 5.0.0.
- `CHANGELOG.md`: `[Unreleased]`를 `[5.0.0] - 2026-09-25`로 바꿨다. 주 버전을 올린 이유, 빠져 있던 변경(minimal의 Git 설정 생성, 코어 규칙 번호 삭제, branch·pr 기본 브랜치 이름, fe-predeploy 수정 범위, `check` 경고 2종 제거), 업데이트 주의, Fixed를 적었다. `[4.2.1]`에 "npm 미배포" 한 줄을 넣었다.
- `README.md`: "아직 릴리스되지 않았다"는 안내를 지웠다. 기존 설치 절에 CI 워크플로의 `@4`를 `@5`로 직접 바꾸라는 항목을 넣었다.
- CI 워크플로 양식: `skills/harness/assets/harness-check.yml`과 `installation.md`의 `guksu-harness@4` → `@5`. `update`가 이 파일을 바꾸지 않는다는 안내를 `installation.md`·`team-customization.md`에 넣었다.
- `import` 결함 수정(`harnessManager.mjs`): 새 minimal `init`이 만든 `.agents/hooks/blockGitMutation.config.json`을 "손대지 않은 파일"로 보지 않아서, `init` → `import` 순서로 하면 팀 묶음의 Git 설정이 건너뛰어졌다. 초기값 그대로인 이 파일은 덮어쓰도록 고쳤다(4.2.1과 같은 동작). 초기값은 상수 `minimalGitConfig` 하나로 두고 생성과 비교에 같이 쓴다. 회귀 테스트 1건 추가.
- 팀 묶음 안내(`team-customization.md`, `installation.md`): 묶음은 프로필을 옮기지 않으므로 기준 저장소가 basic·collaboration이면 `init`에 같은 `--profile`을 주라고 적었다. 3-way 병합은 추적 중인 양식에만 적용된다고 범위를 고쳤다.
- 없어진 코어 규칙 번호를 가리키던 곳: `hooks-and-permissions.md`("규칙 6"), `fe-predeploy/references/quality.md`("절대 규칙 6"), `validateHarness.mjs` 경고 문구 2개, `docs/templates/history.md`("절대 규칙 7" — 이제 번들 양식과 같은 내용).
- 자동 연결이 없어진 설명: `handoff`·`retro`·`fe-craft` 스킬의 "하네스 연동" 절을 "팀이 선택한 경우에만 연결"로 바꿨다. `testing-guide.md`의 오케스트레이터·Workflow 모드 드라이런을 협업 진행표 기준으로 바꿨다.
- 삭제된 개념을 쓰던 양식: `history/assets/templates/`의 `retro.md`(qa-report·워크로그), `loop-spec.md`(워크로그), `design.md`(라이트/풀 티어), `predeploy.md`(사용자 확정 단계).
- 끊긴 안내: `fe-craft`의 feSkills 경로(`../harness/scripts/feSkills.mjs`)와 검증 수단 서열 설명, `harness/SKILL.md`에서 가리키는 곳이 없던 `design-dialogue.md`·`plain-output.md`·`context-economy.md` 안내 한 줄.

점검 방법: 읽기 전용 에이전트 7개가 서로 다른 기준(배포 표면, harness 스킬, 다른 스킬, 교차 참조, 코드와 문서 비교, docs 폴더, 버전 고정)으로 저장소를 훑었다. 중복을 합친 41건을 파일별 검증 에이전트가 반박을 시도하며 다시 확인했고 37건이 남았다. 마지막 점검 에이전트가 4건을 더 찾았다.

| 반영하지 않은 것 | 이유 |
|------|------|
| `blockSecretAccess.mjs` 2행 주석의 "(절대 규칙 6)" | 코어 훅 파일이라 주석만 바꿔도 모든 설치본의 업데이트 대상이 되고, 이 훅을 고친 팀은 충돌을 겪는다. 동작 영향이 없어 남겼다 |
| `installation.md` "최소 구성으로 전환" 제목에 버전 붙이기 | 틀린 내용이 아닌 표기 선호 |
| `harness/SKILL.md` 33행 프로필 설명 보강 | 틀린 내용이 아니다. 같은 내용이 README·installation.md에 있다 |
| 이전 작업 기록의 후속 항목(`2026-09-21-npx-bin-fix.md`, `2026-09-25-lean-harness.md`) | 당시 시점의 기록이다. 이 저장소는 지난 기록의 후속 항목을 되돌아가 고치지 않는다 |

## 4. 확인 필요 · 후속

- 머지 후 main에서 `npm publish`를 실행한다. `prepublishOnly`가 `npm run check`와 `npm test`를 먼저 실행한다.
- 배포 뒤 저장소 밖 빈 디렉터리에서 `npx --yes guksu-harness@5 --help`가 사용법을 출력하는지 확인한다.
- 원하면 `v5.0.0` 태그와 GitHub 릴리스를 만든다. 이 저장소에는 아직 태그가 없다.
- 기존 `--ci` 사용자에게 워크플로의 `@4`를 `@5`로 바꾸라고 알린다.

## 5. 주의사항

- 4.2.1은 npm에 없다. 4.x 사용자는 npx가 무동작하는 4.2.0에 머물러 있으므로 5.0.0으로 올려야 한다.
- 이미 만든 `.github/workflows/harness-check.yml`은 `update`가 바꾸지 않는다. `@4`로 두면 CI가 아무 검사 없이 통과한다.
- 코어 규칙 번호가 없어졌다. 팀 문서나 팀 에이전트가 "절대 규칙 N"을 가리키면 직접 고쳐야 한다.
