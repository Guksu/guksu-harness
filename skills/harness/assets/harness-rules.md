# 하네스 절대 규칙 — 정본

이 파일이 하네스 절대 규칙의 **단일 출처**다. 오케스트레이터·에이전트 정의는 규칙 전문을 복제하지 않고 이 파일을 포인터로 참조한다("작업 전 `docs/harness-rules.md`를 읽는다"). 복제본은 반드시 드리프트한다 — 규칙 수정은 이 파일 한 곳에서만 한다.

이 파일은 **작업하는 쪽이 매 작업 전에 읽는다** — 그래서 여기 있는 것은 작업 중에 지켜야 할 것뿐이다. 하네스를 설계·구축할 때의 규칙(컨텍스트 경제, 실행 모드 선택 등)은 `harness` 스킬에 있다.

규칙 1(git)·6(시크릿)의 실제 강제 수단은 산문이 아니라 **훅·deny 권한**이다(blockGitMutation·blockSecretAccess·branchGuard). 이 문서는 에이전트가 이유를 이해하기 위한 요약이다.

1. **git 작업은 사용자 전담.** commit·push·merge·branch 삭제를 에이전트가 수행하지 않는다. 종료 시 "커밋은 직접 진행하세요"로 안내만 한다. 예외 2종(모두 사용자 승인 기반): ① 사용자 확인된 브랜치 전환은 `branch` 스킬이 `git switch(-c)`로만 수행. ② 사용자가 명시 요청한 커밋·PR 업로드는 `pr` 스킬이 git-flow(main·dev·feat) 절차로 수행(`allowCommitPush` 옵트인 필요). 이때도 커밋 메시지·PR 본문에 Claude 작성 표기(Co-Authored-By 등)는 절대 넣지 않는다 — 훅이 기계적으로 차단한다. merge·rebase·force push·브랜치 삭제·PR 머지는 예외 없이 사용자 전담.
2. **코드를 생성하면 TDD가 기본.** 인수조건 = 테스트 케이스(Red→Green→Refactor), 종료 기준에 테스트 전체 통과 포함. 외부 인프라(DB·외부 SDK)는 모킹/스모크로 분리. 테스트는 설계 문서에 기록된 **합의된 공개 경계(seam — 호출자가 쓰는 인터페이스)** 에 쓴다 — 구현 내부에 결합된 테스트는 리팩토링마다 깨져 유지비만 남긴다.
3. **작업 산출물과 기록을 구분한다.** 역할 간에 주고받는 작업 산출물(계획서·구현 노트·QA 리포트)은 `_workspace/`에 쓰고 읽는다 — 이번 작업 동안만 살고 커밋되지 않는다. **보존되는 기록은 `docs/history/` 문서 하나뿐이다: PR 하나 = 문서 하나.** 작업이 끝나면 흐름을 끝까지 본 쪽이 `_workspace/` 산출물을 근거로 하나로 종합해 `docs/history/{YYYY-MM-DD}-{slug}.md`에 남긴다(`history` 스킬). 역할마다 각자 기록을 남기면 같은 작업이 여러 문서로 흩어져 어느 것이 전체인지 알 수 없다.
4. **단일 출처 문서를 따른다.** 프로젝트의 설계·컨벤션 문서가 있으면 그것이 정본이다. 어긋나면 임의 판단하지 말고 사용자에게 확인한다.
5. **QA는 경계면 교차검증 + incremental.** 존재 확인이 아니라 생산자(API/쿼리)↔소비자(훅/화면)를 동시에 읽고 shape을 비교한다. 전체 완성 후 1회가 아니라 모듈 완성 직후마다. 자기가 만든 것을 자기가 검증하지 않는다 — 같은 맹점을 공유한다.
6. **시크릿은 읽지도 기록하지도 않는다.** `.env`·credential·키 파일을 읽지 않고, 산출물·로그·보고에 토큰/키/비밀번호를 옮겨 적지 않는다. 기록은 보존되는 파일이므로(규칙 3) 기록된 시크릿은 곧 유출이다. 설정값이 필요하면 키 이름만 언급한다.
7. **출력은 읽는 사람이 이해할 수 있게 쓴다.** 질문·보고·문서 등 사용자에게 보이는 모든 출력에 적용한다. 독자는 "이 대화를 보지 못했고 코드를 모르는 사람"으로 가정한다. 전문용어는 써도 되지만 처음 나올 때 한 줄로 풀이하고, 한 문장에는 하나의 내용만 담고, 약어·영문 용어를 풀이 없이 나열하지 않는다. **순서는 결론 → 사용자가 할 일 → 근거다** — 첫 문장은 무엇이 어떤 상태로 끝났는가(실패·검증하지 못한 것이 있으면 그것부터), 이어서 사용자가 결정·실행할 것, 상세는 파일 경로로 보낸다. 파일 경로·명령·수치는 산문이 아니라 표·목록·코드 블록에 두고, 항목 비교·판정·흐름은 긴 글보다 표·배지·다이어그램이 짧다. 어렵게 쓴 글은 사용자의 결정을 늦추고 답변의 질을 떨어뜨린다. 상세: guksu-harness `harness` 스킬의 `references/plain-output.md`.
