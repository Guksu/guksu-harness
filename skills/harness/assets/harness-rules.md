# 하네스 작업 규칙 — 정본

프로젝트의 공통 작업 규칙이다. 도메인 스킬·에이전트는 전문을 복제하지 않고 이 파일을 가리킨다. 이 파일은 코어가 소유하며 관리 도구가 새 버전으로 덮어쓴다. 팀이 바꾸거나 더할 규칙은 `docs/harness-rules.md`(팀 규칙)에 쓴다. 팀 규칙이 이 파일보다 우선한다.

1. **git은 요청한 범위에서 수행한다.** 분석만 요청하면 브랜치·파일을 바꾸지 않는다. 구현에 필요한 안전한 작업 브랜치는 기존 승인 범위에서 준비한다(`branch`). 커밋·푸시·PR은 사용자 요청과 프로젝트 설정을 따른다(`pr`). 이력 재작성·force push·브랜치 삭제·머지는 일반 작업에 포함하지 않는다. 작성자 표기와 브랜치 전략은 프로젝트 정책이다.
2. **변경에 맞는 검증을 수행한다.** 동작 변경·버그 수정은 실패를 재현하는 테스트부터 작성하고 공개 인터페이스에서 검증한다. 문구·문서·가역적인 작은 변경은 관련 검사로 충분하며 의미 없는 테스트를 만들지 않는다. 실행하지 못한 검사는 명시한다.
3. **기록은 작업 단위로 남긴다.** 의미 있는 변경·커밋·PR 또는 기록 요청에 `docs/history/` 문서 하나를 작성·갱신한다(`history`). 작은 수정마다 문서를 만들지 않는다. 역할 간 임시 자료는 `_workspace/`에 두고 커밋하지 않는다. 보존 문서는 임의로 삭제하지 않는다.
4. **기존 프로젝트 규칙을 따른다.** 설계·컨벤션 문서와 기존 결정을 먼저 확인한다. 이미 승인된 내용은 다시 묻지 않는다. 해결되지 않은 충돌이 결과나 권한 범위를 바꿀 때만 질문하고, 확인 가능한 사실은 직접 조사한다.
5. **연결된 기능까지 검사한다.** 데이터를 만드는 쪽(API·쿼리)과 쓰는 쪽(화면·호출자)의 형태와 동작을 함께 확인한다. 모듈 완성 시 관련 검사를 실행한다. 독립 검토는 영향이 큰 변경에 사용하며, 작은 작업마다 에이전트를 추가하지 않는다.
6. **민감정보를 읽거나 기록하지 않는다.** 실제 `.env`·인증정보·키 파일을 읽거나 로그·보고서에 값을 옮기지 않는다. 설정이 필요하면 키 이름만 사용한다. 훅과 deny는 지원되는 도구 경로의 실수를 줄이며 모든 우회를 막는 보안 경계는 아니다.
7. **결과를 쉽게 설명한다.** 결론 → 사용자가 할 일(있을 때) → 근거 순으로 쓴다. 실패·미완·미검증을 숨기지 않는다. 전문용어는 처음에 풀어 쓰고, 한 문장에는 하나의 내용을 담는다. 이전 대화를 읽지 않은 사람도 이해할 수 있어야 한다.
