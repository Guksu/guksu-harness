# Guksu Harness — 에이전트 & 스킬 아키텍트

도메인 요청을 **에이전트(누가) + 스킬(어떻게) + 오케스트레이션(언제, 어떤 순서로)**의 세 층으로 분해해 하네스를 구축하는 메타 스킬.

## 핵심 원칙

1. **세 층을 분리한다.** 스킬은 "어떻게", 에이전트는 "누가", 오케스트레이터는 "언제·어떤 순서"만 담는다. 한 파일에 섞이면 재사용이 죽는다.
2. **실행 모드는 에스컬레이션 사다리다 — 단일 우선.** 직접 실행 → 서브 에이전트 1개 → 루프 → Workflow → 에이전트 팀 순으로, 더 싼 모드로 안 되는 근거(로직 과다·도구 유사도 과부하)가 있을 때만 한 칸 올라간다. 멀티에이전트는 채팅 대비 ~15배 토큰이며 대부분의 코딩 작업에 부적합하다 — 기본값이 아니라 정당화가 필요한 예외다 → `references/execution-modes.md` §1.
3. **모델은 세션 상속이 기본.** 에이전트 호출·정의에 모델을 하드코딩하지 않는다. 오버라이드는 작업 특성이 확실할 때만, 이유 주석과 함께. 이유: 하드코딩된 모델명은 모델 세대가 바뀌는 순간 하네스 전체를 구식으로 만든다.
4. **컨텍스트는 공공재다.** 상시 로딩(CLAUDE.md ~200줄·description)은 포인터 수준으로 최소화하고, 파일 한정 지침은 `.claude/rules/` + `paths:`로 내리고, 대량 읽기·리서치는 서브 에이전트로 격리해 요약만 회수하고, 대형 로그·데이터는 스크립트로 전처리한다. SKILL.md 본문 500줄 이내, 세부는 references/로. 플랫폼이 자동으로 하는 것(프롬프트 캐시·CLAUDE.md 세션당 1회 로드·스킬/MCP 지연 로딩)은 재구현하지 않는다 → `references/context-economy.md`
5. **하네스는 진화하는 시스템이다.** 실행 피드백을 에이전트·스킬·CLAUDE.md에 반영하고 변경 이력을 남긴다.
6. **산문보다 기계적 강제, 페르소나보다 계약.** 지켜야 할 규칙은 훅·deny 권한·검증 게이트로 강제하고, 산문 지침은 이유 전달용 최소한으로 남긴다. 현행 모델은 "당신은 ~역할입니다" 같은 정체성 부여나 일하는 방법의 세부 지시 없이도 작업 명세(입출력 계약·산출물 경로)만으로 잘 수행한다 — 하네스가 커질수록 늘려야 하는 것은 계약과 게이트지 지시문이 아니다.
7. **구축보다 설계 합의가 먼저다.** 신규 구축은 파일을 만들기 전에 사용자와의 반복 문답(Phase 1 설계 문답)으로 설계를 확정하고 문서로 승인받는다. 승인 없는 설계는 추측이고, 추측 위에 지은 스캐폴딩은 재작업 후보다.

## 절대 규칙 — 생성하는 모든 하네스에 내장한다

아래 규칙 7종이 하네스의 불변 조건이다. **내장 방식은 복제가 아니라 단일 출처 배포다**: Phase 2에서 `assets/harness-rules.md`를 프로젝트 `docs/harness-rules.md`로 복사하고, 오케스트레이터·에이전트 정의에는 "작업 전 `docs/harness-rules.md`를 읽는다" 포인터 한 줄만 넣는다. 규칙 전문을 여러 파일에 복제하면 반드시 드리프트한다.

1. **git 작업은 사용자 전담.** commit·push·merge·branch 삭제 등 git 변경 명령을 에이전트가 수행하지 않는다. 종료 시 "커밋은 직접 진행하세요"로 안내만 한다. 예외는 2종이며 모두 사용자 승인 기반이다: **① 사용자 확인된 브랜치 전환** — 작업 시작 전 `branch` 스킬이 사용자 승인을 받아 `git switch(-c)`로만 수행한다. 보호 브랜치(main 등) 위 파일 편집은 branchGuard 훅이 차단한다. **② 사용자가 명시적으로 요청한 커밋·PR 업로드** — `pr` 스킬이 git-flow(main·dev·feat, PR 베이스는 dev) 절차로 commit·push·PR 생성까지 수행한다(`allowCommitPush` 옵트인 필요). 이때도 **커밋 메시지·PR 본문에 Claude 작성 표기(Co-Authored-By: Claude·Generated with Claude Code 등)는 절대 넣지 않는다** — 훅이 표기가 든 커밋을 기계적으로 차단한다. merge·rebase·force push·브랜치 삭제·PR 머지는 예외 없이 사용자 전담이다.
2. **코드를 생성하는 하네스는 TDD가 기본.** 인수조건 = 테스트 케이스(Red→Green→Refactor). 종료 기준에 테스트 전체 통과를 포함한다. 외부 인프라(DB·외부 SDK)는 모킹/스모크로 분리. 테스트는 **사전 합의된 공개 경계(seam)** 에 쓴다 — 모든 것을 테스트할 수 없으므로 어느 경계를 지킬지 설계 문답에서 합의하고 설계 문서에 기록한다. 구현 내부에 결합된 테스트는 리팩토링마다 깨져 유지비만 남긴다.
3. **작업 산출물과 기록을 구분한다.** 역할 간에 주고받는 작업 산출물(계획서·구현 노트·QA 리포트)은 `_workspace/`에 쓰고 읽는다 — 이번 작업 동안만 살고 커밋되지 않는다. **보존되는 기록은 `docs/history/` 문서 하나뿐이다: PR 하나 = 문서 하나.** 작업이 끝나면 흐름을 끝까지 본 쪽이 `_workspace/` 산출물을 근거로 종합해 `docs/history/{YYYY-MM-DD}-{slug}.md`에 남긴다(`history` 스킬, 템플릿 `docs/templates/history.md`). 역할마다 각자 기록을 남기면 같은 작업이 여러 문서로 흩어져 어느 것이 전체인지 알 수 없다 — 기록의 가치는 개수가 아니라 한 작업에 하나라는 데서 나온다.
4. **단일 출처 문서를 따른다.** 프로젝트에 설계 문서·컨벤션 문서가 있으면 그것이 단일 출처다. 어긋나면 임의 판단하지 말고 사용자에게 확인한다.
5. **QA는 경계면 교차검증 + incremental.** 존재 확인이 아니라 생산자(API/쿼리)↔소비자(훅/화면)를 동시에 읽고 shape을 비교한다. 전체 완성 후 1회가 아니라 모듈 완성 직후마다 실행한다. 자기가 만든 것을 자기가 검증하지 않는다 — 같은 맹점을 공유한다. 역할을 나눌 유일한 필수 근거가 이것이다.
6. **시크릿은 읽지도 기록하지도 않는다.** `.env`·credential·키 파일을 읽지 않고, 산출물·로그·보고에 토큰/키/비밀번호를 옮겨 적지 않는다. 기록은 보존되는 파일이므로(규칙 3) 기록된 시크릿은 곧 유출이다. 설정값이 필요하면 키 이름만 언급한다.
7. **출력은 읽는 사람이 이해할 수 있게 쓴다.** 질문·보고·문서 등 사용자에게 보이는 모든 출력에 적용한다. 전문용어는 써도 되지만 처음 나올 때 한 줄로 풀이하고, 한 문장에는 하나의 내용만 담고, 약어·영문 용어를 풀이 없이 나열하지 않는다. 어렵게 쓴 글은 사용자의 결정을 늦추고 답변의 질을 떨어뜨린다 — 설계 문답의 질문에서 특히 그렇다.

**규칙은 늘리지 않는다.** 규칙 하나는 이 하네스가 만드는 모든 에이전트가 매 작업 전에 지불하는 고정비다. 새 제약이 필요하면 먼저 훅·deny로 기계화할 수 있는지 보고(핵심 원칙 6), 도메인 한정이면 규칙이 아니라 그 도메인 스킬에 넣는다.

규칙 1(git)·6(시크릿)은 지침으로만 두지 않고 생성하는 하네스의 `.claude/settings.json`에 훅·deny 권한으로 기계적으로 강제한다 → `references/hooks-and-permissions.md` (Phase 2에서 구성).

## 인자 해석 — `/harness <인자>`

슬래시 명령어로 호출되면 인자로 Phase 0 분기를 선결정한다. 인자가 없거나 아래 패턴에 맞지 않으면 Phase 0 감사 결과로 판단한다. 어느 경우든 Phase 0의 감사(파일 확인 + validateHarness)는 생략하지 않는다 — 현황을 모르면 어떤 분기도 안전하지 않다.

| 인자 패턴 | 분기 | 실행 범위 |
|----------|------|----------|
| 구축, 구성, 설계 | 신규 구축 | Phase 0~4 전체 |
| 점검, 감사, 현황, 동기화 | 운영/유지보수 | Phase 0 + 불일치 수정 |
| 추가, 확장, 수정 + {대상} | 기존 확장 | 영향 범위만 Phase 1~3 |
| 해체, 제거, 철거 + {대상?} | 해체 | Phase 0 해체 절차 |
| {자유 서술 도메인 요청} | Phase 0 감사로 판단 | — |

## 워크플로우

### Phase 0: 현황 감사

1. `프로젝트/.claude/agents/`, `프로젝트/.claude/skills/`, `프로젝트/CLAUDE.md`를 읽는다.
2. `scripts/validateHarness.mjs <프로젝트 경로>`를 실행해 구조 결함(frontmatter 누락, 끊긴 references 링크, name-디렉토리 불일치)을 잡는다.
3. 분기를 결정하고 사용자에게 실행 계획을 보고한다:
   - **신규 구축** — 에이전트/스킬이 없음 → Phase 1부터 전체 실행
   - **기존 확장** — 에이전트/스킬 추가·아키텍처 변경 → 영향 범위만 Phase 1~3 부분 실행 (중복 검토 필수)
   - **운영/유지보수** — 점검·동기화·수정 → 감사 결과의 불일치 목록을 하나씩 수정하고, 수정마다 CLAUDE.md 변경 이력 갱신 + 재검증
   - **해체** — 하네스 전체 또는 일부(에이전트·스킬 단위) 제거 → 아래 해체 절차 실행

**해체 절차** — 구축의 역순이며 순서가 중요하다:

1. **범위 확정** — 전체인지 부분인지. 부분이면 오케스트레이터·다른 에이전트 정의·CLAUDE.md에서 해당 항목을 참조하는 곳을 모두 역추적한다.
2. **참조 제거 → 파일 삭제 순서로 진행한다.** 반대로 하면 살아있는 정의가 죽은 파일을 가리키는 dead link가 생긴다. 훅·permissions에 하네스가 추가한 항목(`references/hooks-and-permissions.md` 참조)도 함께 정리한다.
3. **CLAUDE.md 정리** — 전체 해체면 하네스 섹션 삭제, 부분이면 변경 이력에 제거 사실과 사유를 기록.
4. **산출물(`docs/`·`_workspace/`)은 감사 추적 자료다** — 임의 삭제하지 않고 보존/삭제를 사용자에게 확인한다.
5. **재검증** — validateHarness error 0건 + 남은 스킬 description 간 트리거 충돌 재점검.

### Phase 1: 설계 문답 → 설계

1. **도메인 분석** — 핵심 작업 유형(생성·검증·편집·분석), 기술 스택, 데이터 모델, 단일 출처 문서 파악. 사용자의 숙련도를 대화 맥락에서 감지해 커뮤니케이션 톤을 맞춘다. 이 분석은 다음 단계(설계 문답)의 질문거리를 준비하는 조사다 — 파악한 것은 묻지 않고 확인만 한다.
2. **설계 문답 (신규 구축 필수)** — 파일을 하나라도 만들기 전에 사용자와의 반복 문답으로 시스템 설계를 확정한다. 한 번 묻고 끝내지 않는다: 매 라운드 ① 이전 답변 전체를 현재 설계 초안으로 종합해 보여주고(라운드 간 모순 점검) → ② `AskUserQuestion`으로 질문 2~4개(한 라운드 = 한 주제) → ③ 답변을 설계 문서에 반영, 을 반복한다. **끝나는 시점은 라운드 수가 아니라 수렴이 정한다** — 아래 4조건이 충족되면 1라운드에도 끝나고, 안 되면 5라운드도 간다. 종료 조건은 4가지 모두: 새 미해결 질문 없음 + 라운드 간 모순 0 + 침묵된 가정 0(확인 없이 전제한 것은 질문으로 전환하거나 합의 후 기록) + 최종 설계 요약에 사용자 승인. 승인된 설계 문서(`docs/design/{YYYY-MM-DD}-{slug}.md`, 템플릿 `design.md`)가 이후 절대 규칙 4의 단일 출처다. 라운드 절차·주제 사다리·질문 작성 규칙: `references/design-dialogue.md` (이 단계에서 반드시 읽는다). 기존 확장은 영향 범위에 대해서만, 운영·해체는 생략.
3. **실행 모드 선택** — 설계 문답에서 확인된 내용을 근거로, 사다리 순서로 판별한다(절대 원칙이 아니라 순서가 규칙이다). 첫 질문: *"단일(직접 실행 또는 서브 에이전트 1개)로 안 되는 근거가 있는가?"* — 근거(로직 과다·도구 유사도 과부하)가 없으면 올라가지 않는다. 있다면 *"제어 흐름을 지금 코드로 쓸 수 있는가?"*로 Workflow와 팀을 가른다.

   | 모드 (사다리 순 — 아래로 갈수록 비싸다) | 선택 기준 | 조율 수단 |
   |------|----------|----------|
   | **직접 실행** | 오케스트레이션 자체가 불필요 — 대부분의 작업 기본값 | 현재 세션 |
   | **서브 에이전트** | 컨텍스트 격리·단일 전문성이 필요한 단발 위임, 결과만 회수 | `Agent` 도구 |
   | **루프** | 반복·수렴형("될 때까지"), 종료를 기계적으로 검증 가능 | `loop` 스킬 — 명세 + 검증자 게이트·/loop·Workflow 반복 |
   | **Workflow** | 흐름이 사전 결정 가능(팬아웃·파이프라인·반복), 대량 항목, 스키마 검증된 산출물 | `Workflow` 도구 스크립트 |
   | **에이전트 팀 (최후)** | 진행 중 협상·피드백 루프(기획↔구현↔QA)가 본질, 중간 산출물 상호 참조 | `Agent(name)` 스폰+`SendMessage`+`TaskCreate` (암시적 단일 팀) |
   | **하이브리드** | Phase별 특성이 다름 | Phase마다 위 모드 조합 |

   상세 기준·패턴·예시: `references/execution-modes.md` (이 단계에서 반드시 읽는다)

   **루프는 사용자 확인이 선행된다.** 요청이 루프 후보("~할 때까지", "알아서 계속", "자율로")로 판별되면 임의로 루프를 돌리지 않는다 — `loop` 스킬로 루프 사용 여부와 4요소(트리거·실행 단위·검증자·종료 규칙), 안전장치(최대 반복·**토큰 예산** — 초과 시 자동 중단·보고)를 사용자에게 확인받은 뒤 실행한다.
4. **티어 결정 — 실행 모드가 산출물 규모를 결정한다.** 사다리 판정 결과에 따라 Phase 2에서 만들 것이 달라진다. 티어를 어긴 스캐폴딩(직접 실행 하네스에 오케스트레이터 생성 등)은 조율 대상 없는 조율 문서만 남긴다.

   | 티어 | 실행 모드 | Phase 2 산출물 |
   |------|----------|---------------|
   | **라이트** | 직접 실행 · 서브 에이전트 1개 | 도메인 스킬 + 훅·권한 + 규칙 파일 + 템플릿 2종(history·handoff) + CLAUDE.md 포인터. **에이전트 정의·오케스트레이터는 만들지 않는다** |
   | **풀** | 루프 · Workflow · 에이전트 팀 · 하이브리드 | 라이트 티어 전체 + 에이전트 정의 + 오케스트레이터 + 템플릿 4종(+retro·loop-spec) |

   라이트에서 시작한 하네스가 커지면 그때 풀로 올린다(기존 확장 분기) — 처음부터 풀로 짓는 것은 사다리를 오케스트레이션에서 지키고 스캐폴딩에서 어기는 것이다.
5. **에이전트 분리** (풀 티어만) — 전문성·병렬성·컨텍스트·재사용성 4축으로 판단. 기존 에이전트/스킬과의 중복을 먼저 검토한다 → `references/agent-design.md`

### Phase 2: 구축

모든 산출물은 승인된 설계 문서(Phase 1 설계 문답)에 근거한다 — 구축 중 설계와 다른 결정이 필요해지면 임의로 바꾸지 않고 사용자 확인 후 설계 문서를 먼저 갱신한다(규칙 4). Phase 1의 티어 판정에 따라 항목을 선별한다 — 라이트 티어는 2·4번과 5번의 축소본(규칙 파일 + history·handoff 템플릿)만 실행한다.

1. **규칙 파일 배포** — 이 스킬의 `assets/harness-rules.md`를 프로젝트 `docs/harness-rules.md`로 복사한다(이미 있으면 보존 — 프로젝트 사본이 단일 출처). 이후 만드는 오케스트레이터·에이전트 정의에는 규칙 전문 대신 포인터 한 줄("작업 전 `docs/harness-rules.md`를 읽는다")만 넣는다.
2. **스킬 생성** — `프로젝트/.claude/skills/{name}/SKILL.md`. description은 적극적(pushy)이되 짧게, 본문은 Why 중심·명령형·500줄 이내로 → `references/skill-authoring.md`
3. **에이전트 정의** (풀 티어만) — `프로젝트/.claude/agents/{name}.md`. 파일화 조건: 팀 모드 팀원이거나, 세션 간 재사용되거나, Workflow `agentType`으로 연결될 때. 그 외 단발 위임은 정의 파일 없이 작업 프롬프트 + 스킬 포인터로 충분하다. 템플릿은 페르소나가 아니라 계약(입출력·에러 핸들링) 중심: `references/agent-design.md`
4. **오케스트레이터** (풀 티어만) — 실행 모드별 골격·데이터 전달 프로토콜·에러 핸들링·후속 작업(부분 재실행) 지원: `references/orchestrator-template.md`. 기존 확장이면 새로 만들지 말고 기존 오케스트레이터를 수정한다.
5. **훅·권한 구성** — 도구·명령을 위험 3등급(low=allowlist / medium=기본 / high=deny·훅·확인)으로 분류한 뒤 등급에 맞는 강제 수단을 붙인다. 절대 규칙 1(git)·6(시크릿)과 보호 브랜치는 high 등급의 사례다: 이 스킬의 `assets/hooks/` 훅 3종(git 변경 차단 + Bash 경유 시크릿 접근 차단 + 보호 브랜치 편집 차단(branchGuard — `branch` 스킬과 한 쌍))을 프로젝트 `.claude/hooks/`로 복사해 PreToolUse에 등록하고, permissions deny(Read 도구 측)와 함께 2중 방어를 구성한다. **PR 플로우(규칙 1 예외 ②)는 옵트인이다** — 사용자에게 활성화 여부를 확인받고, 승인 시에만 `blockGitMutation.config.json`에 `{ "allowCommitPush": true }`를 쓰고 git-flow 채택 시 branchGuard의 `protectedBranches`에 `dev`를 추가한다(`pr` 스킬 참조). 이 옵트인을 켜면 **기록 게이트**(`docs/history/` 변경 없는 push 차단 — 절대 규칙 3의 기계적 강제)가 함께 켜진다: 끄려면 같은 config에 `requireHistoryDoc: false`, PR 베이스가 `dev`가 아니면 `historyBase`를 명시한다. 새 도메인은 그 도메인의 high 등급 도구(결제·배포·프로덕션 DB 등)를 재분류해 훅·deny를 추가한다. 에이전트가 반복 실행할 테스트·빌드 명령은 allowlist로 사전 허용해 자율 실행이 권한 프롬프트에 끊기지 않게 한다. 코드 생성 하네스면 검증자 게이트(Stop 훅 — 검증 명령 통과까지 턴 종료 차단 + 토큰 예산·최대 반복 안전장치, TDD 게이트의 일반화)를 사용자 확인 후 선택 적용 → `references/hooks-and-permissions.md`
6. **공통 템플릿 배포** — 절대 규칙 3의 기록 형식을 구체화한다: 이 플러그인 `history` 스킬의 템플릿(이 스킬 기준 `../history/assets/templates/`)을 프로젝트 `docs/templates/`로 복사한다(이미 있으면 보존 — 프로젝트 사본이 단일 출처). **라이트 티어는 `history.md`·`handoff.md` 2종만**, 풀 티어는 4종(`history.md`·`handoff.md`·`retro.md`·`loop-spec.md`)을 복사한다. 설계서 템플릿(`design.md`)은 설계 문답을 거쳤다면 Phase 1에서 이미 복사되어 있다. **프론트엔드(웹 UI) 도메인이면** `predeploy.md`도 함께 복사하고 네 시점(설계 판정·구현·제작 품질·배포 게이트)의 스킬을 배선한다 → `references/frontend-domain.md`. 훅과 같은 이유로 베껴 쓰지 않고 그대로 복사한다.

   **`_workspace/`를 gitignore에 추가한다** — 역할 간 작업 산출물이 커밋에 섞이면 규칙 3의 구분(휘발성 산출물 vs 보존 기록)이 무너진다.

   **종료 의례는 작업 1건당 문서 1개다.** 에이전트 정의(또는 도메인 스킬)에 "작업 산출물은 `_workspace/`에, 완료 시 `docs/history/`에 기록(`history` 스킬)"을, 에러 핸들링에 "세션 중단·작업 인계 시 인계 문서 작성(`handoff` 스킬)"을 명시한다. 회고(`retro` 스킬)는 매 실행 제안이 아니라 Phase 4의 트리거(같은 피드백 2회·반복 실패) 충족 시에만 제안한다. 절차 상세는 `history`·`handoff`·`retro`·`loop` 스킬 참조.

### Phase 3: 검증

1. **구조 검증** — `node {이 스킬 경로}/scripts/validateHarness.mjs <프로젝트 경로>` 실행, error 0건 확인.
2. **트리거 검증** — should-trigger / should-NOT-trigger 쿼리(near-miss 중심)로 description을 점검.
3. **실행 테스트** — 현실적 테스트 프롬프트 2~3개로 실제 실행, 가능하면 with/without-skill 비교.
   방법론 상세: `references/testing-guide.md`
4. (풀 티어) 오케스트레이터에 `## 테스트 시나리오` 섹션(정상 1 + 에러 1 이상)이 있는지 확인한다.
5. **컨텍스트 경제 점검** — CLAUDE.md 포인터 ~200줄 이내, 파일 한정 지침의 `.claude/rules/` 분리, 대량 읽기 단계의 서브 에이전트 격리 여부를 확인한다 → `references/context-economy.md` §3

### Phase 4: 등록과 진화

1. **CLAUDE.md 포인터 등록** — 트리거 규칙 + 변경 이력 테이블만. 에이전트/스킬 목록·디렉토리 구조는 넣지 않는다(파일 시스템과 오케스트레이터가 단일 출처이므로 중복).

   ````markdown
   ## 하네스: {도메인명}

   **목표:** {한 줄}

   **트리거:** {도메인} 관련 작업 요청 시 `{orchestrator-skill}` 스킬을 사용하라. 단순 질문은 직접 응답 가능.

   **변경 이력:**
   | 날짜 | 변경 내용 | 대상 | 사유 |
   |------|----------|------|------|
   | {YYYY-MM-DD} | 초기 구성 | 전체 | - |
   ````

2. **실행 후 피드백 수집** — 매 실행 완료 후 개선점을 묻는다(강요하지 않되 기회는 제공). 산출물 근거의 체계적 회고는 `retro` 스킬로 실행한다(분석 → 제안 → 승인 → 적용).
3. **피드백 반영 경로** — 결과물 품질→해당 스킬, 역할 문제→에이전트 정의, 순서 문제→오케스트레이터, 트리거 누락→description. 모든 변경은 변경 이력에 기록한다. 같은 피드백이 2회 반복되거나 에이전트가 반복 실패하면 사용자가 요청하지 않아도 진화(`retro` 스킬 실행)를 제안한다.
