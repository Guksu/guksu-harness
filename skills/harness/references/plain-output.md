# 사용자 대면 출력 — 독자 기준 작성 (절대 규칙 7 상세)

절대 규칙 7("출력은 읽는 사람이 이해할 수 있게 쓴다")의 상세. 하네스의 출력물은 결국 사람이 읽는다 — 채팅 종료 보고, 작업 기록, 인계 문서, 배포 점검 판정, 리뷰 결과, 설계 문답의 질문, 하네스 구축 계획. 정확한데 읽히지 않는 출력은 없는 출력과 같다.

**원천.** Anthropic 커뮤니티 플러그인의 `eli5` 스킬(Thariq Shihipar, 2026-08)은 10줄짜리 SKILL.md 하나로 "아무것도 모르는 사람에게, 그림은 크게 글은 적게" 출력 정책만 바꿔 설명 품질을 끌어올렸다. 새 능력을 더한 게 아니라 **독자 가정과 매체 제약**을 고정한 것이다. 이 문서는 그 원리를 하네스의 보고·기록 출력에 옮긴다. 설계 문답의 질문 작성 규칙은 `design-dialogue.md` §5가 정본이며, 이 문서는 그것을 보고·기록으로 확장한다.

## 1. 독자 모델

출력 하나에 독자는 셋이다. 셋 모두를 만족시키는 최소공배수 독자를 가정한다.

| 독자 | 무엇을 못 보나 | 무엇이 필요한가 |
|------|--------------|---------------|
| 요청한 사용자 | 도구 호출·중간 출력. 긴 채팅은 스크롤로 사라진다 | 결론과 자기 할 일이 첫 화면에 |
| 다음 세션·다른 에이전트 | 이 대화 전체 | 대화 맥락 없이 읽히는 파일 |
| 코드를 모르는 이해관계자 | 파일 구조·용어·내부 명칭 | 풀어 쓴 용어, "그래서 어떻게 되는가" |

**기본 가정: "이 대화를 보지 못했고, 코드를 모른다."** 이 독자가 결론과 할 일을 알 수 있으면 나머지 둘도 만족한다. 사용자의 숙련도가 높다고 판단되면 용어 풀이를 줄일 수는 있지만, 구조(§2)는 바꾸지 않는다 — 숙련자도 결론부터 읽는다.

## 2. 구조 — 결론 → 할 일 → 근거

| 순서 | 내용 | 길이 |
|------|------|------|
| 첫 문장 | **결론** — 무엇이 어떤 상태로 끝났는가. 검증하지 못한 것이 있으면 그것을 먼저 | 1문장 |
| 둘째 블록 | **사용자가 할 일** — 결정·승인·직접 실행할 것. 없으면 "없음" | 1~3항목 |
| 나머지 | **근거** — 무엇을 바꿨고 어떻게 확인했는가. 상세는 파일 경로로 | 표·목록 |

"무엇을 했는가"는 마지막이다. 사용자는 과정이 아니라 결과와 자기 몫을 알고 싶어 한다 — 과정은 작업 기록(`docs/history/`)이 보존한다(절대 규칙 3).

**실패·미완은 숨기지 않는다.** 테스트가 실패했으면 결론 문장에 실패가 들어간다. "대부분 완료"는 결론이 아니다 — 무엇이 안 됐는지가 결론이다.

## 3. 문장 규칙

- 한 문장에 한 생각. 20단어 안팎, 동사가 있는 문장으로.
- 라벨과 콜론("변경: 파일 3개") 대신 문장("파일 3개를 바꿨다").
- 괄호·화살표·세미콜론으로 문장을 이어 붙이지 않는다. 새 문장을 시작한다.
- 자기 추론을 서술하지 않는다 — "먼저 ~를 확인해 보니", "~라고 판단해서"는 독자에게 정보가 아니다.
- 세션 중에 지어낸 이름으로 부르지 않는다 — "1차 접근", "플랜 B" 같은 명칭은 대화를 못 본 독자에게 무의미하다.
- 마무리 제안·재진술을 붙이지 않는다. 내용이 끝나면 글도 끝난다.

## 4. 용어와 이름

- **첫 등장에 한 줄 풀이.** 약어는 풀어 쓰고(INP → 반응 지연 지표 INP), 하네스 내부 명칭은 "무엇을 하는 것"으로 붙인다: "branchGuard 훅(보호 브랜치 편집을 막는 장치)".
- **비유는 한 번만.** README 용어 사전처럼 "컨텍스트 = 책상 크기" 식 비유는 도움이 되지만, 같은 글에서 반복하면 유치해진다.
- **역할 이름보다 행동.** "qa-inspector가 승인했다"보다 "검증 담당 에이전트가 테스트 통과를 확인했다".

## 5. 코드·경로·수치는 산문 밖으로

| 종류 | 어디에 | 규칙 |
|------|-------|------|
| 파일 경로·함수명 | 표·목록 | 독자가 실제로 가야 할 곳만. 문장당 1개, 문단당 2개까지. 나머지는 말로 풀어 쓴다 |
| 명령·에러 메시지·스니펫 | 코드 블록 | 산문에 섞지 않는다. 그대로 복사해 쓸 수 있게 |
| 수치·건수 | 표 또는 한 줄 | **결정을 바꾸는 수치만.** "테스트 74→77종"은 표에, "약 3초 걸렸다"는 삭제 |
| 판정(pass/fail, 완료/중단) | 배지·표 첫 열 | 색·굵기로 한눈에. 산문 속 "통과했습니다"보다 표 한 줄 |

산문에 경로가 셋 이상 늘어서면 그건 목록이다. 목록으로 바꾼다.

## 6. 글보다 그림 — 형식 선택표

"무엇이 어디로 가는가", "무엇이 무엇과 비교되는가"는 글로 쓰면 길고 그림으로 그리면 짧다.

| 전달할 것 | 형식 | 예 |
|----------|------|-----|
| 항목별 상태·판정 | 표 + 배지 | 검증 결과표, 배포 점검표 |
| 전후 비교 | Before / After / Why 표 | 리뷰 결과 (fe-craft) |
| 흐름·순서·경계면 | mermaid 다이어그램 | 데이터 전달, 에이전트 순서, 생산자↔소비자 |
| 선택지와 영향 | 표 (선택지 / 영향 / 기본 동작) | 확인 필요 항목, 설계 문답 선택지 |
| 명령·에러 | 코드 블록 | 재현 명령, 실패 출력 |
| 한 줄 논리 | 산문 | 결론, 이유 |

그림이 어울리는 내용을 산문으로 쓰고 있다면 멈추고 형식을 바꾼다. 반대로 한 줄이면 되는 결론을 표로 만들지 않는다 — 형식은 내용의 모양을 따른다.

## 7. 매체별 형식

| 매체 | 첫 요소 | 길이·구성 | 상세는 어디로 |
|------|--------|----------|-------------|
| 채팅 종료 보고 | 결론 1문장 | 3~5문장 + 할 일 + 경로. 헤더 없음 | 작업 기록 파일 |
| 작업 기록 (`history.md` §1 개요) | 결론 1문장 | 2~4문장 — 어떻게 끝났고 왜 했나 | §2 작업 내용·§3 검증 결과 |
| 인계 문서 (`handoff.md`) | 목표 + 상태 | 근거 경로 병기, 다음 단계는 행동 문장 | 산출물 파일 |
| 배포 점검 (`predeploy.md`) | 종합 판정(배포 가능/불가) | fail은 "사용자에게 어떤 일이 생기는가"로 풀이 | 근거 수치 열 |
| 리뷰 결과 (fe-craft) | 심각도순 요약 | Before/After/Why 표 — Why에 원칙 이름 + 한 줄 풀이 | 참조 원칙 문서 |
| 설계 문답 질문 | 결정 하나 | 선택지마다 결과·추천안 표기 (`design-dialogue.md` §5) | 설계서 |
| 하네스 구축 계획 (harness Phase 0~1) | 판정(신규/확장/유지보수) + 티어 | 사용자가 답할 질문을 먼저, 근거는 표 | references/ 문서 |

## 8. 안티패턴

- **경로 나열 산문** — "`a.ts`, `b.ts`, `c.ts`를 수정하고 `d.test.ts`를 추가했으며…". 목록·표로.
- **근거 없는 완료 선언** — "완료했습니다". 무엇으로 확인했는지 없으면 결론이 아니다.
- **실패 묻기** — 통과 항목을 길게 쓰고 실패를 끝에 한 줄로. 실패가 결론이다.
- **과정 서술** — "~를 시도했고 안 돼서 ~로 바꿨다". 인계 문서의 "시도와 결과" 섹션에만 둔다.
- **헤더 남발** — 500단어 미만의 글에 헤더는 없다. 그 이상이어도 셋까지.
- **내부 명칭 그대로** — "verifierGate가 stuckAfter로 중단". 무엇이 왜 멈췄는지로 풀어 쓴다.
- **숫자 산문** — "테스트 74개 중 74개가 통과했고 3개를 추가해 77개가 되었으며…". 표 한 줄.

## 9. Before / After

### 채팅 종료 보고

**Before**

> 먼저 기존 훅 구조를 확인한 뒤 `blockGitMutation.mjs`, `branchGuard.mjs`, `hooks.test.mjs`를 수정했고, `allowCommitPush` 옵션 처리 로직을 리팩토링했습니다. 테스트는 대부분 통과했는데 `hooks.test.mjs`의 force push 케이스 1개가 실패해서 추가 확인이 필요할 것 같습니다. 작업 기록도 작성했습니다. 추가로 필요한 게 있으면 말씀해 주세요!

**After**

> force push 차단 테스트 1건이 실패한 상태로 끝났습니다. 커밋·푸시 허용 옵션은 동작하지만, 그 옵션이 켜진 상태에서 force push가 여전히 막히는지는 확인되지 않았습니다.
>
> 할 일: 실패 케이스를 고칠지, 옵션 사양을 바꿀지 결정이 필요합니다.
>
> | 구분 | 내용 |
> |---|---|
> | 변경 | git 차단 훅 2개, 훅 테스트 1개 |
> | 검증 | 훅 테스트 21/22 통과 |
> | 기록 | `docs/history/2026-09-04-allow-commit-push.md` |

### 작업 기록 개요

**Before**

> 사용자 요청에 따라 PR 플로우 관련 작업을 진행함. 여러 파일을 검토하고 필요한 변경을 적용함.

**After**

> 사용자가 명시 요청할 때만 커밋·PR을 올릴 수 있게 git 차단 훅에 옵트인 옵션을 추가했다. 옵션이 꺼진 기본 상태의 동작은 바뀌지 않았다. 옵션이 켜져도 force push와 Claude 작성 표기 커밋은 계속 차단된다.

## 10. 점검 질문

출력을 내보내기 전에, 그리고 harness Phase 3에서 생성된 템플릿·종료 절차를 검토할 때 아래를 묻는다. 하나라도 "아니오"면 고친다.

1. 첫 문장만 읽은 사람이 무엇이 어떻게 끝났는지 아는가?
2. 사용자가 지금 해야 할 일이 둘째 블록 안에 있는가(없으면 "없음"이 적혀 있는가)?
3. 검증하지 못한 것·실패한 것이 결론보다 뒤에 숨어 있지 않은가?
4. 이 대화를 못 본 사람이 모르는 이름·약어가 풀이 없이 등장하지 않는가?
5. 산문 속에 경로가 셋 이상, 수치가 둘 이상 들어 있지 않은가?
6. 표·다이어그램이 더 짧을 내용을 산문으로 쓰고 있지 않은가?
