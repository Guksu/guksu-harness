# 프론트엔드 도메인 — fe-skills 라이브러리 배선

프론트엔드(웹 UI) 하네스를 구축할 때만 읽는다. 프론트엔드 작업은 **설계 → 구현 → 제작 품질 → 배포 가부**의 네 시점이 뚜렷하고, 각 시점의 담당이 이미 존재한다. 이 문서는 그 넷을 언제 어디에 연결하는지 정한다.

## 1. 네 시점과 담당

| 시점 | 담당 | 출처 |
|------|------|------|
| 코드 **전** — 화면 설계 판정 | `list-filter-detail` · `infinite-feed` | **fe-skills 라이브러리** (fe-system) |
| 구현 | UI 패턴 29종 (`bottom-sheet`·`pinch-zoom` 등) | **fe-skills 라이브러리** (fe-ui) |
| 제작 **중** — 품질 | `fe-craft` | 이 플러그인 |
| 배포 **직전** — 게이트 | `fe-predeploy` | 이 플러그인 |

넷은 경쟁하지 않는다 — 시점이 다르다. `fe-craft`는 판정하지 않고 개선하며, `fe-predeploy`는 개선하지 않고 판정한다. 라이브러리는 만들 것을 주고, `fe-craft`는 만든 것을 다듬는다.

## 2. fe-skills는 설치하는 플러그인이 아니라 가져다 쓰는 라이브러리다

[`Guksu/fe-skills`](https://github.com/Guksu/fe-skills)에는 UI 패턴 29종의 **실행 가능한 정본 코드**(의존성 0 코어 + CSS + React 래퍼)와 화면 설계 판정 2종이 있다. 플러그인으로 설치하면 description 31개가 모든 프로젝트의 모든 턴에 상시 로딩되므로, 대신 **필요한 하나만 조회해서 가져온다** — npm에서 쓸 패키지만 받아 쓰는 것과 같다. 상시 로딩 비용은 0이다.

클라이언트는 이 스킬의 `scripts/feSkills.mjs`다:

```bash
node {스크립트 경로}/feSkills.mjs find <사용자 요청 문장>   # 후보를 순위대로
node {스크립트 경로}/feSkills.mjs get <slug> --into <대상>  # SKILL.md 경로 + 정본 코드 복사
node {스크립트 경로}/feSkills.mjs list                      # 전체 목록
```

첫 실행에서 얕은 클론을 캐시에 받고(`$XDG_CACHE_HOME/guksu-harness/fe-skills`), 이후에는 캐시를 쓴다. 갱신에 실패해도 캐시가 있으면 그것으로 진행한다 — 낡은 라이브러리가 없는 라이브러리보다 낫다. 캐시도 네트워크도 없으면 exit 3으로 알린다. **이때 작업을 멈추지 않는다**: 직접 구현하고 그 사실을 작업 기록에 남긴다.

## 3. 사용자가 요청하지 않아도 먼저 조회한다

이것이 배선의 핵심이다. 사용자는 "fe-skills 써줘"라고 말하지 않는다 — "바텀시트로 메뉴 고르게 해줘"라고 말한다. 그래서 **UI 패턴을 구현하거나 목록·피드 화면을 설계하는 작업이 생기면, 요청 여부와 무관하게 라이브러리를 먼저 조회한다.**

Phase 2에서 다음을 수행한다:

1. **스크립트를 프로젝트로 복사한다** — 이 스킬의 `scripts/feSkills.mjs`를 프로젝트 `.claude/scripts/`로 복사한다(훅과 같은 이유로 베껴 쓰지 않고 그대로 복사). 복사해 두면 그 프로젝트는 이 플러그인이 설치되지 않은 세션에서도 라이브러리를 쓸 수 있다.
2. **도메인 스킬 또는 developer 에이전트 정의의 "규칙과 기록" 절에 아래를 넣는다:**

```markdown
- **UI 패턴 구현·화면 설계는 fe-skills 라이브러리를 먼저 조회한다.** 직접 짜기 전에
  `node .claude/scripts/feSkills.mjs find "<사용자 요청 문장>"`을 실행한다.
  - 후보가 나오면 `get <slug> --into <대상 디렉토리>`로 가져와 SKILL.md를 읽고, 그 정본 코드를
    프로젝트 컨벤션에 맞춰 적용한다. 이미 모션·접근성·`prefers-reduced-motion`이 정리된 코드다.
  - 후보가 없거나(0건) 라이브러리를 못 가져오면(exit 3) 직접 구현하고, 그 사실과 이유를
    작업 기록에 남긴다.
  - 완료 기준: 패턴 구현을 시작하기 전에 `find`를 실행했고, 후보가 있었다면 그 SKILL.md를 읽었다.
- UI를 구현·수정할 때는 `fe-craft`의 기준(디자인 8원칙·모션·React 성능)을 참조한다.
- 배포 전에는 `fe-predeploy` 게이트를 통과해야 한다 — blocker fail이 있으면 배포 불가로 보고한다.
```

**완료 기준을 빼지 않는다.** "먼저 찾아봐라"만 적으면 바쁜 실행에서 건너뛰어진다 — 판별 가능한 기준(`find`를 실행했는가)이 있어야 강제된다(skill-authoring "단계에는 완료 기준을 단다").

오케스트레이터(풀 티어)에는 종료 절차의 배포 게이트만 명시한다 — 라이브러리 조회는 작업하는 쪽이 판단할 일이지 조율할 일이 아니다.

## 4. 가져온 코드의 출처를 남긴다

라이브러리에서 가져온 정본 코드는 프로젝트에 복사되어 그 프로젝트의 코드가 된다. `get`이 출처(저장소·slug·MIT)를 출력하므로, **작업 기록의 "2. 작업 내용"에 어느 패턴을 가져왔는지 적는다.** 나중에 라이브러리가 개선됐을 때 무엇을 다시 가져와야 하는지 알 수 있는 유일한 근거다.

`get`은 덮어쓴 파일을 보고한다 — 프로젝트에서 수정한 사본이 있었다면 조용히 지우지 않고 diff를 확인한다.

## 5. 템플릿

`predeploy.md`를 `docs/templates/`에 함께 복사한다(`fe-predeploy`가 쓴다). 나머지는 문서를 따로 남기지 않는다 — 설계 판정 결과는 설계 문서에, 구현·비평 결과는 코드에, 최종 요약은 `docs/history/` 기록에 들어간다.
