# 프론트엔드 도메인 — 스킬 배선

프론트엔드(웹 UI) 하네스를 구축할 때만 읽는다. 프론트엔드 작업은 **설계 → 구현 → 제작 품질 → 배포 가부**의 네 시점이 뚜렷하고, 각 시점을 담당하는 스킬이 이미 존재한다. 이 문서는 그 넷을 언제 어디에 연결하는지만 정한다.

## 1. 네 시점과 담당

| 시점 | 담당 스킬 | 출처 | 하는 일 |
|------|----------|------|---------|
| 코드 **전** — 설계 판정 | `list-filter-detail` · `infinite-feed` | **fe-system** (별도 마켓플레이스) | 상태 위치·데이터 페칭·복귀 복원 등을 신호 판독으로 결정 |
| 구현 | 29종 UI 패턴 (`bottom-sheet`·`pinch-zoom` 등) | **fe-ui** (별도 마켓플레이스) | 패턴별 정본 코드(의존성 0 코어 + CSS + React 래퍼) |
| 제작 **중** — 품질 | `fe-craft` | 이 플러그인 | 디자인 8원칙 비평·모션 리뷰·React 성능 ("더 좋게 만들 수 있는가") |
| 배포 **직전** — 게이트 | `fe-predeploy` | 이 플러그인 | pass/fail 판정 + 체크리스트 기록 ("배포해도 되는가") |

넷은 경쟁하지 않는다 — 시점이 다르다. `fe-craft`는 판정하지 않고 개선하며, `fe-predeploy`는 개선하지 않고 판정한다. `fe-ui`는 만들고, `fe-system`은 만들기 전에 결정한다.

## 2. fe-ui · fe-system은 별도 마켓플레이스다

[`Guksu/fe-skills`](https://github.com/Guksu/fe-skills)의 플러그인 2종이며, **이 플러그인에 흡수하지 않는다.** 이유는 상시 로딩 비용이다: `fe-ui` 29종의 description은 설치한 모든 프로젝트의 모든 턴에 로딩되는데, 백엔드·CLI 프로젝트에는 순수 비용이다. 프론트엔드 프로젝트만 설치하는 편이 옳다(핵심 원칙 4).

설치는 사용자가 한다 — 하네스가 대신 설치하지 않고 **안내한다**:

```
/plugin marketplace add Guksu/fe-skills
/plugin install fe-ui@fe-skills        # UI·애니메이션 구현 패턴
/plugin install fe-system@fe-skills    # 화면 설계 판정
```

**설치 여부를 확인받고 배선한다.** 설치하지 않기로 하면 그 줄은 넣지 않는다 — 없는 스킬을 가리키는 포인터는 dead link이고, 에이전트가 찾다가 실패하면 그 정의 전체의 신뢰가 떨어진다.

## 3. 어디에 배선하는가

**Phase 1 설계 문답에는 넣지 않는다.** 설계 문답의 대상은 *하네스 자체*(어떤 역할·스킬·안전장치를 만들 것인가)이고, `fe-system`의 대상은 *기능의 구현 설계*(이 목록 화면의 상태를 어디에 둘 것인가)다. 다루는 것이 달라서 경쟁하지 않는다.

배선 지점은 **구축된 하네스가 실제 요청을 받는 자리** — 도메인 스킬 또는 developer 에이전트 정의다. 아래 4줄을 그 정의의 "규칙과 기록" 절에 넣는다(설치한 것만):

```markdown
- 목록·피드처럼 상태 설계가 필요한 화면은 코드를 쓰기 전에 `list-filter-detail`·`infinite-feed`(fe-system) 스킬로 설계를 판정한다.
- UI 패턴(바텀시트·핀치줌·캐러셀 등)은 직접 짜기 전에 fe-ui 스킬에 해당 패턴이 있는지 먼저 찾는다 — 있으면 그 정본 코드를 가져와 프로젝트 컨벤션에 맞춘다.
- UI를 구현·수정할 때는 `fe-craft`의 기준(디자인 8원칙·모션·React 성능)을 참조한다.
- 배포 전에는 `fe-predeploy` 게이트를 통과해야 한다 — blocker fail이 있으면 배포 불가로 보고한다.
```

오케스트레이터(풀 티어)에는 종료 절차의 배포 게이트만 명시하면 된다 — 나머지 셋은 작업하는 쪽이 판단할 일이지 조율할 일이 아니다.

## 4. 템플릿

`predeploy.md`를 `docs/templates/`에 함께 복사한다(`fe-predeploy`가 쓴다). 나머지 셋은 문서를 남기지 않는다 — 설계 판정 결과는 설계 문서에, 구현·비평 결과는 코드에, 최종 요약은 `docs/history/` 기록에 들어간다.
