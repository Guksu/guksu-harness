# 필요한 결정만 질문하기

사용자의 요청과 기존 프로젝트 규칙에서 목표·범위·완료 기준을 먼저 읽는다. 코드·도구·현재 브랜치처럼 확인 가능한 사실은 직접 조사한다.

## 기본 구성

기존 규칙을 보존하고 도메인 스킬·공통 보호 장치를 추가하는 기본 구성은 변경 목록을 보여 주고 진행한다. 사용자가 “추천대로 진행”, “제안한 개선을 적용”이라고 했으면 그 범위의 승인을 다시 요청하지 않는다. 설정하지 않은 권한은 열지 않는다.

## 질문이 필요한 경우

- 요구사항이 서로 충돌하며 어느 쪽을 택하느냐에 따라 결과가 달라진다.
- 외부 배포·영구 권한 확대·기존 자산 삭제가 필요하지만 요청에 포함되지 않았다.
- 역할 간 책임·입출력·완료 기준이 불명확해 협업 구조를 정할 수 없다.

질문은 한 번에 한 주제로 묶고 추천안과 선택의 영향을 쓴다. 이미 답한 항목이나 사용자가 승인한 선택은 반복하지 않는다. 질문에 의존하지 않는 조사는 계속한다.

## 설계 기록

복잡한 신규 구축이나 역할 구조 변경은 `history` 스킬의 `assets/templates/design.md`를 사용해 `docs/design/{날짜}-{이름}.md`에 목표·책임·검증·미결정을 기록한다. 작은 수정은 별도 설계서를 만들지 않는다.

종료 조건은 구현에 필요한 결정이 정리되고 요청 범위에 들어오는 것이다. 모든 사소한 선택을 사용자에게 승인받는 “미확인 가정 0건”을 목표로 삼지 않는다. 중요한 가정만 드러내고, 기존 규칙으로 판단할 수 있는 구현 선택은 근거와 함께 진행한다.

설계를 바꾸더라도 이미 승인된 목표 안의 가역적인 구현 변경이면 기록하고 진행한다. 사용자 요구나 권한 범위를 바꾸는 경우에만 다시 확인한다.
