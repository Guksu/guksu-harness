# 실행 방식 선택

실행 방식은 작업에 필요한 만큼만 구성한다. 직접 실행, 반복 실행, 역할 분리를 한 줄의 비용 순위로 취급하지 않는다. **반복한다고 협업 구성이 필요한 것은 아니다.**

## 1. 직접 실행이 기본

현재 세션에서 목표를 수행하고 결과를 검증할 수 있으면 직접 실행한다. 별도 역할 정의나 진행표를 만들지 않는다. 에이전트를 추가하면 맥락 전달·조율·검토 비용이 생기며 비용 배수는 작업마다 다르다.

## 2. 세 가지 판단

| 질문 | 선택 |
|---|---|
| 현재 세션에서 처리할 수 있는가? | 직접 실행 |
| 독립적인 조사·검토가 필요하고 결과만 받아도 되는가? | 사용 가능한 위임 도구로 단발 위임 |
| 여러 역할이 반복적으로 산출물을 주고받아야 하는가? | 필요한 역할과 진행표를 정의 |

반복 여부는 별도로 판단한다. 수정 후 테스트를 다시 실행하는 일은 직접 실행에 포함한다. 세션 밖 예약·감시·대량 반복은 `loop` 스킬로 실행 수단과 한도를 정한다.

## 3. 정해진 처리 흐름

여러 항목을 같은 순서로 처리한다면 스크립트로 흐름과 재시도를 표현할 수 있다. 사용 가능한 도구를 먼저 확인하고, 특정 `Workflow` API나 예산 API가 있다고 가정하지 않는다.

입력 항목 → 처리 → 검증 → 결과 저장 → 실패 항목만 재시도 순서를 명시한다. 최대 반복·시간 한도와 재시작 위치를 저장한다. 일반 테스트 재시도에 이 기반시설을 만들지 않는다.

## 4. 에이전트 팀

실제 협상·중간 산출물 교환·독립 검토가 필요한 역할만 분리한다. 작업 범위와 입력·출력 경로를 정하고 모델은 세션에서 상속한다. 순차 의존 작업을 역할 수만 늘려 병렬 작업이라고 부르지 않는다.

정의 파일은 재사용할 역할에만 만든다. 설계 방법은 `agent-design.md`, 진행표는 `orchestrator-template.md`를 따른다.

## 5. 단발 위임

대형 자료 요약이나 독립 검토처럼 경계가 명확한 작업에 사용한다. 조사 대상·답해야 할 질문·결과 형식을 전달한다. 파일 변경이 필요 없다면 읽기 전용으로 지정한다. 결과를 받은 쪽은 근거를 확인해 최종 작업에 반영한다.

## 6. 반복 실행

장시간 처리·감시·예약은 요청에서 목표, 실행 간격, 종료 조건, 한도를 확인한다. 이미 정해진 내용은 다시 묻지 않는다. 누락된 중요한 결정만 질문한다. `loop` 스킬이 실제 환경에 맞는 수단을 선택한다.

검증 명령 통과는 필요한 증거지만 요구사항 충족 전체와 동일하지 않다. 시각·실행 결과가 필요한 목표는 해당 증거도 확인한다. 판단할 수 없는 항목은 미검증으로 보고한다.

## 7. 대량 변환

파일별로 변환 → 검증 → 제한된 재시도를 수행한다. 결과를 저장해 실패한 항목만 다시 실행할 수 있게 한다. 예산과 범위를 넘는 항목은 실패 목록으로 남긴다. 기계적 검증이 부족하면 자동 성공으로 처리하지 않는다.
