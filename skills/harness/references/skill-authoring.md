## 1. 스킬 구조

```
skill-name/
├── SKILL.md          (필수: YAML frontmatter + 본문)
├── scripts/          (선택: 반복·결정적 작업용 실행 코드 — 로딩 없이 실행 가능)
├── references/       (선택: 조건부 로딩하는 참조 문서)
└── assets/           (선택: 출력에 쓰이는 템플릿·이미지)
```

frontmatter의 `name`은 디렉토리명과 일치시킨다 (`validateHarness.mjs`가 검사한다).

## 2. Description — 유일한 트리거 메커니즘

description은 항상 컨텍스트에 존재하는 유일한 부분이며, 스킬이 트리거될지를 전적으로 결정한다. Claude는 트리거를 보수적으로 판단하므로 **적극적(pushy)으로** 작성한다.

**나쁜 예:** `"PDF 문서를 처리하는 스킬"`
**좋은 예:** `"PDF 읽기, 텍스트/테이블 추출, 병합, 분할, 암호화 등 모든 PDF 작업을 수행. .pdf 파일을 언급하거나 PDF 산출물을 요청하면 반드시 이 스킬을 사용할 것."`

**포함할 것:**
1. 스킬이 하는 일 (구체적 동사로 나열)
2. 트리거 상황 — 사용자가 실제로 입력할 표현들. 단, **구분되는 상황(가지)당 대표 표현 1개** — 같은 상황을 다르게 부른 동의어 나열은 트리거 확률이 아니라 고정비만 늘린다. 공식/캐주얼 표기가 실제로 다른 요청 상황을 가리킬 때만 둘 다 싣는다.
3. **후속 작업 키워드** — "다시 실행", "재실행", "업데이트", "수정", "보완", "{부분}만 다시", "이전 결과 개선". 초기 생성 키워드만으로는 후속 요청이 트리거되지 않는다.
4. 유사하지만 트리거하면 안 되는 경우와의 구분 ("단순 질문은 직접 응답 가능" 등)

**길이 규율 — pushy와 장황은 다르다.** description은 모든 세션 모든 턴에 상시 로딩된다 — 스킬이 10개면 description 총량이 곧 하네스의 고정비다. **~350자 이내**를 목표로(validateHarness가 초과 시 경고), "(1)~(4)" 같은 번호 열거·중복 설명을 빼고 트리거 표현 자체만 남긴다. 절차·이유 설명은 본문 몫이다 — description의 역할은 트리거 판정 하나뿐이다.

**트리거 단어를 앞세운다.** 판정에 쓰이는 단어(도메인 명사·행동 동사)를 문장 앞부분에 두고, 스킬의 정체성 서술은 본문에 맡긴다. 이 원칙은 description만이 아니라 **포인터 전반**(CLAUDE.md의 하네스 트리거 줄, 본문의 "언제 이 파일을 읽으라" 줄)에 적용된다 — 상시 로딩되는 포인터는 워딩이 곧 도달성이다: 꼭 읽혀야 할 문서가 안 읽히면 문서를 본문에 인라인하기 전에 포인터 워딩부터 벼린다.

## 3. 본문 작성 원칙

| 원칙 | 설명 |
|------|------|
| **Why를 설명하라** | "ALWAYS/NEVER" 강압 대신 이유를 전달한다. 이유를 이해한 모델은 명시되지 않은 엣지 케이스에서도 올바르게 판단한다. |
| **Lean하게 유지** | 컨텍스트는 공공재다. 무게를 벌지 않는 문장은 삭제하거나 references/로 옮긴다. |
| **일반화하라** | 특정 예시에만 맞는 좁은 규칙(오버피팅) 대신 원리를 쓴다. 피드백을 반영할 때도 그 사례만 고치지 말고 일반 원칙으로 승격시킨다. |
| **반복 코드는 번들링** | 에이전트들이 매번 같은 스크립트를 작성하는 패턴이 보이면 `scripts/`에 미리 번들링한다 (결정적·재사용·컨텍스트 절약). |
| **명령형으로 작성** | "~한다", "~하라" 어조. 설명문이 아니라 작업 지시서다. |
| **양성 진술로 쓴다** | 금지문("~하지 마라")은 금지 대상을 컨텍스트로 끌어들여 오히려 그 행동을 활성화한다. 목표 행동을 직접 진술한다("주석은 한 줄로 쓴다"). 정말 필요한 하드 가드레일은 먼저 훅·deny로 기계적 강제가 가능한지 검토하고(핵심 원칙 6), 산문으로 남겨야 하면 금지문 옆에 목표 행동을 병기한다. |
| **no-op을 삭제한다** | 문장마다 "이 문장이 없어도 모델이 기본으로 하는 행동인가"를 검사한다. 기본 동작을 바꾸지 못하는 문장("철저하게 하라", "신중히 판단하라")은 로딩비만 내는 no-op이다 — 단어를 다듬지 말고 문장째 삭제하거나, 기본을 실제로 이기는 더 강한 요구로 바꾼다. 판정은 논쟁이 아니라 실행으로 한다: 스킬을 돌려 행동이 달라지는지 본다(testing-guide의 with/without 비교). |

### 단계에는 완료 기준을 단다

절차형 본문의 모든 단계는 **완료 기준**(그 단계가 끝났음을 판정하는 조건)으로 끝나야 한다. 두 속성이 품질을 결정한다:

- **판별 가능성** — "이해가 충분해지면"처럼 모호한 기준은 조기 종료를 부른다: 눈앞의 단계를 빨리 끝내고 다음 단계로 넘어가려는 당김을 모호한 기준은 버티지 못한다. "{경로}에 파일이 존재한다", "검증 명령이 0으로 종료한다"처럼 됐다/안 됐다를 기계적으로 판별할 수 있게 쓴다 (loop 스킬의 검증자 원칙과 동일).
- **요구 수준** — 에이전트는 기준이 요구하는 만큼만 일한다. "변경 목록을 만든다"는 대충 훑어도 충족되지만, "수정된 모듈 **전부**가 목록에 근거와 함께 있다"는 전수 조사를 강제한다. 철저함은 "철저히 하라"는 부사(no-op)가 아니라 기준의 요구 수준으로 강제한다.

## 4. Progressive Disclosure

3단계 로딩으로 컨텍스트 비용을 통제한다:

| 단계 | 로딩 시점 | 크기 목표 |
|------|----------|----------|
| Metadata (name+description) | 항상 | ~100단어 |
| SKILL.md 본문 | 스킬 트리거 시 | ≤500줄 |
| references/ · scripts/ | 필요할 때만 (scripts는 로딩 없이 실행) | 제한 없음 |

**크기 관리 규칙:**
- **분리 기준은 분기다.** 모든 실행 경로가 읽는 것은 본문에, 일부 경로만 읽는 것은 references/로 — 일부만 쓰는 참조가 본문에 있으면 모든 경로가 그 로딩비를 내고, 절차 단계 사이에 끼면 단계 자체를 묻어버린다.
- SKILL.md가 500줄에 근접하면 세부를 references/로 분리하고, 본문에는 "언제 이 파일을 읽으라"는 포인터를 남긴다.
- 300줄 이상의 reference에는 상단에 목차를 둔다.
- 도메인/플랫폼별 변형은 references/ 하위에 파일을 나눠 관련 파일만 로드되게 한다 (예: `references/aws.md`는 AWS 선택 시에만).

## 5. 스킬-에이전트 연결

- 에이전트 1개 ↔ 스킬 1~N개. 여러 에이전트가 한 스킬을 공유해도 된다.
- 스킬은 "어떻게", 에이전트는 "누가"를 담는다. 에이전트 정의에 작업 절차가 길게 들어가기 시작하면 스킬로 분리할 신호다.
- 에이전트 정의에는 "작업 전 `{skill}` 스킬을 읽어라(또는 Skill 도구로 호출하라)"를 명시해 연결을 끊기지 않게 한다.
