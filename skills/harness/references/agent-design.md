## 1. 분리 기준 4축

에이전트를 나눌지 합칠지는 4축으로 판단한다. 2축 이상에서 분리 이득이 있을 때만 나눈다 — 에이전트가 많을수록 조율 비용이 커진다.

| 축 | 분리하는 경우 | 합치는 경우 |
|----|-------------|------------|
| **전문성** | 요구 지식·판단 기준이 서로 다름 (기획 vs 구현 vs 검증) | 같은 지식으로 처리 가능 |
| **병렬성** | **breadth-first로 분해된다** — 독립된 여러 방향을 동시에 탐색해 벽시계 시간이 줄어듦 | 순차 의존이라 병렬 이득 없음 |
| **컨텍스트** | 한 컨텍스트에 담기엔 입력이 너무 큼 | 컨텍스트 여유 충분 |
| **재사용성** | 다른 워크플로우에서도 단독 호출됨 | 이 워크플로우 전용 |

**병렬성 축의 본질은 토큰 예산 확장이다.** Anthropic 측정에서 멀티에이전트 성능 이득의 80%가 "토큰을 더 쓴 것" 자체로 설명됐다 — 즉 서브 에이전트를 나누는 진짜 효과는 협업이 아니라 **병렬로 컨텍스트 창 용량을 늘리는 것**이다. 따라서 이 축은 작업이 breadth-first(독립 방향 동시 탐색)로 쪼개질 때만 이득이 있다. **순차 의존 작업을 여러 에이전트로 짜면 토큰만 ~15배 쓰고 병렬 이득이 0이다** — 대표적 안티패턴이다. 나누기 전에 "이 조각들이 서로를 기다리지 않고 동시에 갈 수 있는가"를 먼저 답한다(execution-modes.md §1).

**생성자와 검증자는 반드시 분리한다.** 자기 결과물을 자기가 검증하면 같은 맹점을 공유한다.

## 2. 중복·재사용 검토

신규 에이전트/스킬 생성 전 `프로젝트/.claude/agents/`, `.claude/skills/`의 기존 항목과 대조한다. 하네스를 반복 구축하면 역할이 겹치는 에이전트가 다른 이름으로 누적되기 쉽다.

| 판정 | 기준 | 조치 |
|------|------|------|
| 동일 | 역할·입출력이 같음 | 기존 것을 그대로 사용 |
| 포함 | 기존 역할의 부분집합 | 기존 것을 사용, 프롬프트로 범위 한정 |
| 확장 | 기존 역할 + α | 기존 정의를 수정(변경 이력 기록) |
| 신규 | 겹침 없음 | 새로 생성 |

## 3. 정의 파일 — 파일화 조건과 계약 중심 템플릿

**정의 파일은 조건부다.** `프로젝트/.claude/agents/{name}.md`로 파일화하는 것은 다음 중 하나에 해당할 때만이다:

1. **팀 모드 팀원** — 협업 프로토콜(수신·발신·작업 유형)이 명시되어야 팀 품질이 보장된다.
2. **세션 간 재사용** — 같은 역할이 다음 세션·다른 워크플로우에서 다시 호출된다.
3. **Workflow `agentType` 연결** — 스크립트가 커스텀 에이전트 타입으로 참조한다.

그 외 **단발 위임은 정의 파일을 만들지 않는다** — 작업 프롬프트(입력 경로 + 산출물 계약) + 관련 스킬 포인터로 충분하다. 현행 모델은 정체성 부여 없이 작업 명세만으로 역할을 수행한다. 정의 파일이 자동 로드되는 호출(`subagent_type`·`agentType`)에서는 정의 전문을 프롬프트에 중복 포함하지 않는다.

**템플릿은 페르소나가 아니라 계약이다.** "당신은 ~입니다" 같은 정체성 서술과 일하는 방법의 세부 지시(모델이 기본으로 잘하는 것)를 넣지 않는다 — 넣을 것은 이 에이전트만의 책임 범위, 입출력 계약, 에러 핸들링, 도메인 제약이다.

```markdown
---
name: {kebab-case-이름}
description: "{역할 한 줄}. {어떤 작업 시 호출되는지}."
---

# {이름}

## 책임 범위
1~3개. 이 에이전트가 책임지는 결과와 하지 않는 것.

## 규칙과 기록
- 작업 전 `docs/harness-rules.md`(절대 규칙 정본)를 읽는다. 규칙 전문을 여기 복제하지 않는다.
- 프로젝트 컨벤션: `docs/code-convention.md` 등이 있으면 작업 전 읽는다.
- 작업 산출물(계획서·구현 노트·QA 리포트 등 다음 역할이 읽을 것)은 `_workspace/`에 쓴다 — 이번 작업 동안만 사는 채널이다.
- 보존 기록은 작업 흐름을 끝까지 본 쪽이 `docs/history/`에 **작업 1건당 1개** 남긴다(`history` 스킬). 역할마다 각자 기록을 만들지 않는다.
- 도메인별 제약 (비용 가드레일, 보안 규칙, 엣지케이스 처리 등 — 이 에이전트에만 해당하는 것).

## 입력/출력 계약
- **입력**: 읽어야 할 파일 경로 (계획서, 설계 문서).
- **출력**: 산출물 경로 + 형식. 후속 에이전트가 소비할 수 있는 구조로.
- **재호출 시**: 이전 산출물이 존재하면 읽고 개선점을 반영. 사용자 피드백이 주어지면 해당 부분만 수정.

## 팀 통신 프로토콜 (에이전트 팀 모드일 때만)
- **수신**: 누구로부터 무엇을 받는가.
- **발신**: 누구에게 언제 무엇을 보내는가 (예: 모듈 완성 시 QA에게 교차검증 요청).
- **작업 요청**: 공유 작업 목록에서 담당하는 작업 유형.

## 에러 핸들링
- 입력이 모호하면 추측하지 말고 {대상}에게 확인.
- 막히면 리더에게 보고 + 대안 제시 (스킵 시 산출물에 명시).
```

## 4. 모델 정책

- **기본: 모델 파라미터를 생략한다.** 에이전트는 세션 모델을 상속하며, 이것이 거의 항상 옳다.
- **오버라이드는 예외다.** 작업 특성이 확실할 때만(예: 대량 단순 분류 → 경량 모델) 지정하고, 정의 파일이나 호출부에 이유를 한 줄 남긴다.
- **특정 모델명을 정의 파일에 박지 않는다.** 모델 세대가 바뀌면 하네스 전체가 구식이 된다. "최고 추론이 필요하다" 같은 요구사항은 적되, 모델명 매핑은 호출 시점에 판단한다.
- **reasoning effort도 같은 원칙이다.** 기본은 세션 상속(생략). 기계적 단계(단순 분류·포맷 변환)만 `low`로 낮추고, 최난도 검증·심판 단계만 상향하며 이유를 한 줄 남긴다.

## 5. QA 에이전트 가이드

코드 생성 하네스에는 QA 에이전트를 포함하는 것이 기본이다.

**검증 수단 서열 (신뢰도 순 — 가장 높은 가용 수단을 쓴다):** Anthropic이 명시한 순서다.
1. **규칙 기반 피드백** (최상) — 린트·타입체크·테스트·컴파일처럼 종료 코드로 참/거짓이 결정되는 것. 결정적이고 값싸다. 가능하면 항상 이것.
2. **시각·실행 피드백** — 스크린샷·실행 로그·산출물 diff 등 사람/에이전트가 관측할 결과물.
3. **LLM 판정** (최후) — Anthropic이 "robust하지 않은 방법"으로 못박았고 지연도 크다. 규칙 기반이 **불가능할 때만** 보조로 쓰고, **단독 종료 판정에 쓰지 않는다**(loop 스킬 자기평가 금지와 동일 원리). LLM 판정으로 루프를 종료시키는 설계는 금지.

**필수 사항:**
- **타입은 `general-purpose`** — 검증 스크립트·테스트 실행이 필요하므로 읽기 전용 타입(`Explore`)은 불가.
- **핵심은 경계면 교차검증** — "파일이 존재한다"가 아니라, 생산자(API 응답·쿼리·Edge Function)와 소비자(훅·화면·타입)를 **동시에 읽고 shape을 비교**한다. 경계면 버그(필드명 불일치, null 처리 차이, 단위 차이)가 통합 버그의 대부분이다.
- **incremental QA** — 전체 완성 후 1회가 아니라 **각 모듈 완성 직후** 실행한다. 늦게 발견된 경계면 버그는 수정 범위가 누적되어 비싸진다. developer 정의에 "모듈 완성 시 QA에게 교차검증 요청"을, QA 정의에 "발견 즉시 파일:라인 + 수정 방법으로 회신"을 명시한다.
- **TDD 연동** — QA는 테스트의 존재·의미(load-bearing 여부)·통과를 모두 검증한다. 껍데기 단언(테스트가 있지만 아무것도 검증하지 않음)을 잡아낸다.
- **2축 분리 보고** — 리뷰·QA 결과는 **컨벤션 축**(프로젝트 코드 표준·컨벤션 위반)과 **스펙 축**(승인된 설계 문서·요구사항 대비 누락/과잉 구현/오구현 — 절대 규칙 4의 단일 출처가 기준)을 별도 항목으로 보고하고, 두 축을 합쳐 순위를 매기지 않는다. 표준을 다 지키고 엉뚱한 것을 만들 수도, 요구를 다 채우고 컨벤션을 깰 수도 있다 — 합산하면 한 축의 발견이 다른 축을 가린다.

**QA 루프 종료 조건:** 재검증 2~3회 초과 시 잔여 이슈를 산출물에 "미해결"로 명시하고 사용자에게 판단을 요청한다 (무한 루프 방지).

**버그 진단 규율 — 피드백 루프가 90%다.** 테스트 실패·버그 보고를 받은 에이전트(developer·QA)의 진단 절차로 에이전트 정의에 포인터를 남긴다:

1. **루프 먼저, 가설은 나중.** 이 버그에만 빨간불이 켜지는 실행 명령 1개(실패 테스트·curl 스크립트·CLI 재현 — 검증 수단 서열 1과 같은 규칙 기반)를 만들기 전에는 원인 가설을 세우지 않는다. 코드를 읽으며 이론부터 만드는 것이 이 규율이 막는 실패다. 루프는 결정적이고 초 단위여야 한다 — 비결정 버그는 재현 자체가 아니라 **재현율을 끌어올리는 것**(반복 실행·타이밍 압박)이 목표다.
2. **가설은 3~5개를 랭킹해서, 반증 가능하게.** 첫 그럴듯한 가설에 고정되는 것을 막는다. 각 가설은 "X가 원인이면 Y를 바꿨을 때 사라진다"는 예측을 명시한다 — 예측이 없으면 가설이 아니라 감이다.
3. **계측은 가설당 변수 1개, 로그는 고유 태그로.** 디버그 로그에 `[DEBUG-{4자}]` 같은 고유 접두사를 붙인다 — 종료 시 grep 1회로 전량 제거를 검증할 수 있다(태그 없는 로그는 살아남는다).
4. **수정 전에 최소화, 수정 후에 회귀 테스트.** 빨간불이 유지되는 최소 시나리오로 줄인 뒤(남은 요소 전부가 실패에 필요한 상태), 그 시나리오를 회귀 테스트로 전환하고 → 실패 확인 → 수정 → 통과 확인 순서로 간다(TDD 연동).
