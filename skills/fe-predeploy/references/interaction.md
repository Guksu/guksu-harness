# 인터랙션 안정성 · 네트워크 경계 — 검증 레시피

실무 장애의 단골 목록이다. 모든 판정은 계측 숫자(요청 수·DOM 상태·콘솔)로 한다. 시나리오 실행 전 `scripts/instrument.js` 주입이 전제다(browser-recipes.md).

## A. 인터랙션 안정성

### A1. 버튼 연타 → API 1회 (blocker)

- **왜**: 제출 버튼 연타로 주문·결제·게시물이 중복 생성되는 사고는 프론트 장애 1순위다. 서버 멱등성과 별개로 클라이언트가 1차 방어선이다.
- **방법**: `resetRequests()` → 대상 버튼을 config `repeatClicks`(기본 5)회 빠르게 클릭 → `countRequests('<엔드포인트>', 'POST')`. claude-in-chrome이면 `read_network_requests`로 교차 확인.
- **판정**: 해당 엔드포인트 요청 수 **== 1**. 2 이상이면 fail.
- **주의**: 실제 부수효과가 있는 액션(운영 결제 등)은 실행 금지 — 로컬·스테이징에서만.

### A2. 제출 중 pending 상태 표시 (warn)

- **왜**: 요청이 느릴 때 피드백이 없으면 사용자는 연타한다 — A1 사고의 유발 요인.
- **방법**: 클릭 직후 DOM 판독 — 버튼 `disabled` 속성, `aria-busy`, 스피너/로딩 텍스트 존재.
- **판정**: 요청 진행 중 disabled 또는 시각적 pending 표시가 있으면 pass.

### A3. 검색·입력 debounce (warn)

- **왜**: 타이핑마다 요청하면 서버 부하 + 응답 순서 역전으로 낡은 결과가 표시된다.
- **방법**: `resetRequests()` → 검색창에 config `debounceTypingChars`(기본 10)자를 연속 입력 → 요청 수 카운트.
- **판정**: 요청 수 < 입력 글자 수 (이상적으로 1~2회). 글자 수와 같으면 fail.

### A4. 언마운트 후 setState 경쟁 (warn)

- **왜**: 요청 중 페이지를 떠나면 응답 콜백이 언마운트된 컴포넌트의 상태를 만진다 — 콘솔 경고·간헐 크래시.
- **방법**: 응답이 느린 페이지 진입 → 로딩 완료 전 즉시 다른 페이지로 이동 → `report().consoleErrors` + 콘솔 판독.
- **판정**: React 경고("state update on unmounted"류)·에러 0건.

### A5. 폼 검증 (blocker)

- **왜**: 클라이언트 검증이 없으면 잘못된 데이터가 API까지 간다 — 서버 검증이 있어도 UX는 깨진다.
- **방법**: 빈 필수값·잘못된 형식(이메일 등)으로 제출 시도 → 요청 카운트 + 에러 메시지 DOM 확인.
- **판정**: API 미전송 **그리고** 사용자에게 보이는 에러 메시지 표시.

### A6. 뒤로가기·새로고침 후 중복 제출 (warn)

- **왜**: 제출 완료 페이지에서 새로고침·뒤로가기 시 폼이 재전송되거나 상태가 깨지는 고전 사고.
- **방법**: 제출 완료 → 새로고침 → 뒤로가기 → 요청 카운트·화면 상태 확인.
- **판정**: 중복 요청 없음(재전송 확인 다이얼로그 포함 안 뜸), 상태 표시 정상.

### A7. 한글 IME 조합 중 Enter 중복 제출 (blocker)

- **왜**: 한글 조합 중 Enter를 누르면 `keydown`이 중복 발생해 검색·채팅·댓글이 **2회 제출**된다. macOS Chrome에선 조합 중 글자가 input 밖으로 밀려 안 보이는 렌더링 이슈도 있다(bendd.me Chrome 한글 IME 버그 글).
- **방법**: 정적 스캔 `ime-enter-no-composing` → 각 지점에 `e.isComposing`(또는 keyCode 229) 가드 확인. 브라우저에서 한글 입력 직후 즉시 Enter → 요청 카운트.
- **판정**: 한글 입력 + Enter에서 제출 요청 **1건**.

### A8. 다단계 퍼널의 히스토리 정합 (blocker)

- **왜**: 인증·결제 같은 단계형 플로우에서 뒤로가기가 **이미 완료된 단계로 역행**하거나(토스페이먼츠 계좌등록 퍼널 사례 — toss.tech/article/engineering-note-1), 단일 페이지 퍼널이 새로고침에 시작점으로 튕긴다.
- **방법**: 각 단계에서 뒤로가기·새로고침 실행.
- **판정**: 되돌아가면 안 되는 단계(인증 완료 등)가 차단되고, 새로고침 후 현재 단계가 유지(또는 명시적 재시작 안내)된다. A6(중복 제출)과 함께 본다.

## C. 네트워크·API 경계

### C1. 실패 응답 처리 — 무한 로딩 금지 (blocker)

- **왜**: API가 500을 반환할 때 에러 UI가 없으면 사용자는 영원한 스피너를 본다.
- **방법**: 실패를 유도할 수 있는 경로(존재하지 않는 리소스 상세 페이지, 잘못된 파라미터)로 진입 → 에러 UI·재시도 수단 확인. 유도가 불가능하면 skip(사유 기록) 후 코드 리뷰로 대체.
- **판정**: 에러 상태 UI가 표시되고 로딩 표시가 해제된다.

### C2. 로딩 상태 표시 (warn)

- **방법**: 데이터 페이지 진입 직후 스켈레톤·스피너 존재 확인 (네트워크가 빠르면 스로틀링 활용).
- **판정**: 로딩 중 빈 화면·레이아웃 점프가 아니라 명시적 로딩 표시.

### C3. 인증 만료 처리 (warn)

- **왜**: 401에서 무한 로딩·흰 화면이면 사용자는 갇힌다.
- **방법**: 세션 만료 상태를 만들 수 있으면(로그아웃 후 보호 URL 직접 진입) 리다이렉트·안내 확인. 못 만들면 skip + 코드 리뷰 대체.
- **판정**: 로그인 유도(리다이렉트 또는 안내)가 일어난다.

### C4. stale 응답 무시 (warn)

- **왜**: 연속 검색에서 먼저 보낸 요청이 나중에 도착하면 낡은 결과가 최신을 덮는다.
- **방법**: 검색어 A 입력 직후 B 입력 → 최종 화면이 B의 결과인지 확인 (반복 3회).
- **판정**: 항상 마지막 입력의 결과가 표시된다.

### C5. 무한스크롤 — 뒤로가기 복원·페이지네이션 정합 (warn)

- **왜**: 목록→상세→뒤로가기에서 보던 위치로 못 돌아가면 탐색 UX가 무너진다(오늘의집 무한스크롤 개발기 — 전체 재로드 방식은 수십 초 걸려 폐기, 커서 저장으로 해결). 목록이 실시간으로 바뀌는 서비스의 offset 페이징은 항목 중복·누락을 만든다.
- **방법**: 목록을 수 페이지 스크롤 → 상세 진입 → 뒤로가기: 위치·로드 항목 유지 확인. 코드 리뷰로 offset/cursor 방식과 key 중복 가능성 확인.
- **판정**: 뒤로가기 후 위치가 복원되고, 스크롤 중 같은 항목이 두 번 나오지 않는다.
