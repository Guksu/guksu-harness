# 모션 리뷰 — 애니메이션 결정·기준·개선 서열

> **출처**: Emil Kowalski의 [skills 저장소](https://github.com/emilkowalski/skills)(MIT License, Copyright (c) 2026 Emil Kowalski)의 `emil-design-eng`·`review-animations` 스킬을 한국어로 증류·재구성한 스냅샷(2026-08-05)이다. 라이선스 전문은 `../LICENSES.md`. 심화 학습은 [animations.dev](https://animations.dev/), 증류본과 어긋나면 업스트림이 우선한다.

기본 태도: **"돌아가는 모션"이 아니라 "맞게 느껴지는 모션"이 기준이다.** 굼뜨게 느껴지거나, 엉뚱한 지점에서 튀어나오거나, 너무 자주 발동하거나, 프레임이 떨어지는 트랜지션은 통과가 아니라 회귀다. 기본값은 플래그 — 승인은 획득하는 것이다.

## 1. 결정 프레임워크 — 넣기 전에 4가지를 답한다

1. **애니메이션이 필요한가?** 목적(공간적 일관성·상태 표시·피드백·설명·급격한 변화 완충) 없이 "멋있어서"는 자주 보는 요소에선 탈락이다. 확신이 없으면 가장 강한 수는 **삭제**다.
2. **얼마나 자주 보는가?** 빈도가 모션 예산을 결정한다:
   - 키보드 트리거·하루 100회+ 액션(커맨드 팔레트 토글 등) → **무동작**
   - 하루 수십 회 → 축소된 모션
   - 가끔 → 표준 모션
   - 드묾·최초 1회(온보딩·성공 축하) → 딜라이트 허용
3. **어떤 이징인가?** 진입·퇴장은 `ease-out`(즉시 움직임 시작 → 반응성). 화면 위 이동·변형은 `ease-in-out`. 호버·색 변화는 `ease`. 등속 모션(마퀴·프로그레스)만 `linear`. **UI에 `ease-in` 금지** — 사용자가 가장 집중하는 첫 순간을 지연시켜 같은 시간이라도 더 굼뜨게 느껴진다. 빌트인 CSS 이징은 약하다 — 커스텀 cubic-bezier를 쓴다(예: ease-out `cubic-bezier(0.23, 1, 0.32, 1)`, ease-in-out `cubic-bezier(0.77, 0, 0.175, 1)`, 드로어 `cubic-bezier(0.32, 0.72, 0, 1)`).
4. **얼마나 빠른가?** UI는 300ms 이하가 규칙이다. 요소별 예산: 버튼 눌림 100~160ms · 툴팁/소형 팝오버 125~200ms · 드롭다운 150~250ms · 모달/드로어 200~500ms · 마케팅 연출만 그 이상 허용. 체감 성능도 모션이 좌우한다 — 빠른 스피너는 같은 로딩도 빨라 보이게 하고, 첫 툴팁 이후엔 딜레이·애니메이션을 생략하면 툴바 전체가 빨라진 느낌을 준다.

## 2. 비타협 기준 10 — 위반은 곧 발견(finding)이다

1. **정당화된 모션** — "왜 움직이는가"에 답 못 하면 탈락.
2. **빈도 적합** — 위 빈도 표 준수. 키보드 액션 애니메이션은 블록.
3. **반응형 이징** — 진입·퇴장 `ease-out` 또는 강한 커스텀 커브. UI `ease-in`은 블록.
4. **UI 300ms 이하** — 초과는 사유 없으면 발견.
5. **원점·물리적 정합** — 팝오버·드롭다운·툴팁은 트리거에서 스케일(`transform-origin`), 중앙 아님. `scale(0)`에서 시작 금지 — `scale(0.9~0.97)` + opacity로(모달은 중앙 유지 예외).
6. **중단 가능성** — 빠르게 반복 발동(토스트·토글)·제스처 모션은 현재 상태에서 재타게팅되는 transition/스프링으로. 0부터 재시작하는 keyframes는 발견.
7. **GPU 속성만** — `transform`·`opacity`만 애니메이션. `width`/`height`/`margin`/`padding`/`top`/`left`는 성능 발견.
8. **접근성** — `prefers-reduced-motion` 존중(0이 아니라 완화 — opacity·색은 유지, 이동만 제거). 호버 모션은 `@media (hover: hover) and (pointer: fine)`으로 게이트.
9. **비대칭 진입/퇴장** — 의도적 행위(누름·홀드·파괴적 확인)는 느리게, 시스템 응답은 즉각적으로(예: 홀드-삭제 누름 2s linear, 해제 200ms ease-out). 대칭 타이밍은 발견.
10. **응집** — 모션 성격이 컴포넌트·제품 전체와 일치(장난스러움 vs 크리스프한 대시보드). 확신 없으면 삭제가 최선일 때가 많다.

## 3. 즉시 플래그 트리거 (코드에서 기계적으로 잡는다)

- `transition: all` (무제한 속성 애니메이션)
- `scale(0)` 진입, 초기 transform 없는 순수 페이드 진입
- UI 상호작용의 `ease-in`, 의도적 애니메이션의 약한 빌트인 이징
- 키보드 단축키·커맨드 팔레트·고빈도 액션의 애니메이션
- 사유 없는 300ms 초과 UI 지속시간
- 트리거 고정 팝오버·드롭다운·툴팁의 `transform-origin: center`
- 토스트·토글 등 빠른 반복 요소의 keyframes
- 레이아웃 속성(`width`/`height`/`margin`/`padding`/`top`/`left`) 애니메이션
- 부하 중 실행되는 Framer Motion `x`/`y`/`scale` 축약 프로퍼티
- 부모 CSS 변수 갱신으로 자식 transform 구동(스타일 recalc 폭풍)
- 이동 모션의 `prefers-reduced-motion` 미처리, 게이트 없는 `:hover` 모션
- 누름-해제·홀드 상호작용의 대칭 타이밍
- 30~80ms 스태거가 필요한 곳의 일괄 등장

## 4. 개선 서열 — 앞선 수를 먼저 시도한다

1. **삭제** (고빈도·무목적·키보드 트리거)
2. **축소** — 짧은 지속시간, 작은 transform, 적은 속성
3. **이징 교정** — `ease-in`→`ease-out`/강한 커스텀 커브
4. **원점·물리 교정** — `transform-origin` 수정, `scale(0)`→`scale(0.95)`+opacity
5. **중단 가능화** — keyframes→transition, 제스처는 스프링
6. **GPU 이동** — 레이아웃 속성→`transform`/`opacity`, 프로그래매틱 CSS는 WAAPI
7. **비대칭 타이밍** — 의도 단계는 느리게, 응답은 즉각
8. **폴리시** — 크로스페이드 블러 마스킹, 그룹 스태거, 진입 `@starting-style`, 살아있는 요소엔 스프링
9. **접근성·응집** — reduced-motion·호버 게이트 추가, 성격 튜닝

## 5. 리뷰 출력

발견은 Before/After/Why 표 한 개로(행당 이슈 1개), 이어서 영향 티어순 코멘트(느낌 파괴 회귀 → 삭제 대상 → 성능 → 중단성·타이밍 → 원점·응집 → 접근성), 마지막에 명시적 판정:

- **Block** — 느낌 파괴 회귀, 키보드/고빈도 액션 애니메이션, UI의 `scale(0)`/`ease-in`, 쉬운 GPU 대안이 있는 비GPU 애니메이션
- **Approve** — 위 사항 없음 + 지속시간·이징 예산 내 + 필요한 중단성·reduced-motion 처리 완료

## 6. 판정 불가 영역 — 사람 눈을 요청한다

리스트 진입의 opacity+height 조합 같은 미세 튜닝은 공식이 없다 — "맞을 때까지" 조정 영역이므로 수치 제안 후 사용자의 실제 조작 확인을 요청한다. 타이밍 이슈는 슬로모션·프레임 단위 재생으로 점검하고, 완성 판정은 다음날 새 눈으로 다시 보게 권한다.
