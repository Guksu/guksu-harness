# FE Craft — 프론트엔드 제작 품질

"동작한다"와 "완성도 있다" 사이의 간극을 메우는 스킬. 코드만으로는 실제 화면의 배치와 사용감을 확인하기 어렵다 — 이 스킬은 그 판단을 (1) 디자인 8원칙 체크리스트, (2) 모션 리뷰 기준, (3) React 성능 규칙이라는 **언어화된 기준**으로 바꿔 비평·수정 루프를 돌린다.

## fe-predeploy와의 관계

| | fe-craft (이 스킬) | fe-predeploy |
|---|---|---|
| 시점 | 제작·수정 **중** (반복 루프) | 배포 **직전** (1회 게이트) |
| 산출 | 개선된 UI·코드 | pass/fail 판정 + 체크리스트 기록 |
| 질문 | "더 좋게 만들 수 있는가" | "배포해도 되는가" |

이 스킬은 판정하지 않고 개선한다. 배포 가부는 fe-predeploy 몫이다.

## 선택적 패턴 재사용

팀이 fe-skills 라이브러리를 채택했거나 재사용을 요청하면 `../harness/scripts/feSkills.mjs`의 find·get을 사용할 수 있다. 라이브러리 조회를 모든 UI 구현의 선행 조건으로 삼지 않는다. 가져온 코드의 출처·라이선스는 코드 근처 또는 팀이 정한 위치에 남긴다.

## 스크린샷 비평 루프 (디자인 영역의 실행 방법)

코드만 읽고 "잘 됐다"고 판단하지 않는다 — 디자인은 렌더된 결과에만 존재한다. 검증 수단 서열(규칙 기반 > 시각·실행 피드백 > LLM 판정)의 "시각·실행 피드백"을 디자인에 적용한 것이다:

1. **렌더** — 실제 브라우저에서 화면을 띄운다 (브라우저 도구가 있으면 스크린샷 캡처, 없으면 사용자에게 스크린샷을 요청한다).
2. **비평** — `references/design-principles.md`의 8원칙 각각에 대해 관찰(무엇이 보이는가)과 위반(어떤 원칙이 깨졌는가)을 적는다. 원칙 이름을 명시한다 — 언어화가 곧 조향 수단이다.
3. **수정** — 상위 2~3개 위반만 고친다. 한 번에 전부 고치면 무엇이 효과였는지 알 수 없다.
4. **재렌더·비교** — 다시 캡처해 이전과 비교한다. 2~3회 반복이면 대부분 수렴한다.
5. **수렴 판단** — 8원칙에 뚜렷한 위반이 없으면 종료. 미세 취향 영역은 사용자 판단에 맡긴다(비평 결과를 선택지로 제시).

모션은 스크린샷으로 판정할 수 없다 — 느낌 판단이 필요한 모션은 사용자에게 실제 조작 확인을 요청하고, 코드 리뷰로 잡을 수 있는 위반(`references/animation.md`의 즉시 플래그 목록)은 코드에서 잡는다.

## 리뷰 출력 형식

리뷰 요청(코드·화면 비평)의 결과는 Before/After/Why 표로 낸다 — 지적만 있고 수정안이 없는 리뷰는 소비할 수 없다:

| Before | After | Why |
|---|---|---|
| {현재 코드/상태} | {수정안} | {근거 — 위반한 원칙·규칙 이름 + 사용자에게 어떻게 보이는지 한 줄} |

표 뒤에 심각도순 요약과 (리뷰만 요청받은 경우) 적용 여부 질문을 붙인다. Why는 원칙 이름만으로 끝내지 않는다 — "근접 원칙 위반"이 아니라 "근접 원칙 위반 — 라벨과 입력창이 떨어져 어느 항목의 값인지 헷갈린다". 수정까지 요청받았으면 바로 적용한다.

## 원천과 라이선스

세 reference는 외부 공개 자료를 증류·재구성한 것이다 — 출처와 라이선스는 각 파일 상단과 `LICENSES.md`에 명시되어 있다. 증류본과 업스트림이 충돌하면 업스트림이 우선한다(스냅샷 날짜 기준).

## 하네스 연동

팀이 선택한 경우에만 프로젝트 절차에 연결한다. 기본 하네스 설치에는 포함되지 않으며, 배포 전 점검은 fe-predeploy가 맡는다. 독립적으로도 언제든 호출 가능하다.
